Skill นี้ทำหน้าที่รับ **เอกสาร requirement ที่มีอยู่แล้วหนึ่งฉบับ** ใน `docs/01-requirements/01-spec/` แล้วดำเนินการทั้งหมดต่อไปนี้ให้ครบ: สร้าง/อัปเดตเอกสาร features list (MoSCoW), สร้าง/อัปเดตเอกสาร user journey (mermaid diagram) ต่อ persona หลัก, อัปเดต index, และบันทึก log ประจำวัน โดยอ้างอิงธรรมเนียมของ vault ตามที่ระบุใน [CLAUDE.md](../../../CLAUDE.md) ที่ root ของ repo (ภาษาไทย, wikilink, ห้ามลบเอกสาร ฯลฯ)

ทำตามขั้นตอนนี้ตามลำดับ **ห้ามข้ามขั้นตอนใด**:

## ขั้นตอนที่ 1 — เลือก spec doc เป้าหมาย

ถ้าผู้ใช้ระบุ spec doc ที่ต้องการไว้ชัดเจนอยู่แล้ว ใช้ไฟล์นั้นได้เลย

ถ้าผู้ใช้ไม่ได้ระบุ (เช่น เรียกเปล่าๆ ว่า `/spec-to-journey`) ให้ใช้ Glob สำรวจ `docs/01-requirements/01-spec/*.md` (ไม่นับ `index.md`):

- พบไฟล์เดียว → ใช้ไฟล์นั้นทันที
- พบมากกว่าหนึ่งไฟล์ → **default เป็น "ทำทั้งหมด" โดยไม่ต้องถามยืนยัน** วนทำทีละฉบับให้ครบขั้นตอนที่ 2–6 (วิเคราะห์ → ตัดสินใจ → สร้าง/แก้ไฟล์ → บันทึก log) จนจบก่อนขึ้นฉบับถัดไปเสมอ — **ห้ามทำหลายฉบับพร้อมกัน** เพราะการนับ `RUNNING_NO` ในขั้นตอนที่ 5 และการ append เข้าไฟล์ log วันเดียวกันในขั้นตอนที่ 6 ต้องอ่านสถานะล่าสุดของไฟล์ก่อนเขียนทุกครั้ง ทำครบทุกฉบับแล้วค่อยไปขั้นตอนที่ 7 เพื่อสรุปรวมทุก topic ในคำตอบเดียว
- ไม่พบไฟล์ spec เลย → แจ้งผู้ใช้ว่ายังไม่มีเอกสาร requirement ในโปรเจกต์แล้วหยุด (เป็น hard blocker เดียวที่ควรหยุดถาม เพราะไม่มีอะไรให้วิเคราะห์ต่อ)

## ขั้นตอนที่ 2 — วิเคราะห์และร่างเนื้อหา

เรียก subagent ชื่อ `journey-designer` (ผ่าน Agent tool, `run_in_background: false` เพราะต้องใช้ผลลัพธ์ทันทีในขั้นตอนถัดไป) โดยส่ง path ของ spec doc ที่เลือกไปให้ ให้ subagent วิเคราะห์ว่ามีเอกสารออกแบบเดิมที่ derive จาก spec นี้อยู่แล้วหรือไม่ (`new` / `update` / `duplicate` / `ambiguous`) พร้อมแยก persona หลักและร่าง `featuresListMarkdown` + `journeyMarkdown[]` กลับมาด้วย

## ขั้นตอนที่ 3 — ตัดสินใจเองเมื่อข้อมูลไม่ชัดเจน

หลักการ: **ตัดสินใจเองแล้วทำงานต่อให้เสร็จ ห้ามหยุดถามผู้ใช้ระหว่างทาง** ใช้สมมติฐานที่สมเหตุสมผลที่สุดจากบริบทของ spec เอง แล้วจดบันทึกทุกสมมติฐานสำคัญที่ใช้ไว้ (สะสมไว้ข้ามทุก spec doc ที่ทำในรอบนี้) เพื่อรายงานรวมให้ผู้ใช้ทราบในขั้นตอนที่ 7

แนวทางตัดสินใจสำหรับกรณีที่พบบ่อย:

- **จำนวน/การแยก user journey ต่อ persona**: ยึดตามที่ subagent `journey-designer` วิเคราะห์มาใน `personas` โดยตรง (persona ที่มี flow การใช้งานจริงตามรอยเป็นขั้นตอนได้ควรมี journey แยก ส่วน persona ที่มีเพียง action เดียวจบ เช่น "ตั้งค่าพารามิเตอร์" ไม่ต้องมี journey แยก) ไม่ต้องถามผู้ใช้ก่อนเริ่มงาน
- **`relationship: ambiguous`** (พบเอกสารเดิมที่เกี่ยวข้องแต่ subagent ไม่มั่นใจว่าควร update หรือสร้างใหม่): ใช้กฎ default นี้ — ถ้าเอกสารเดิมที่พบ derive จาก spec เดียวกันและเนื้อหาทับซ้อนกับ spec ปัจจุบันเกินครึ่ง ให้เลือก **update** เอกสารนั้นตรงๆ มิฉะนั้น (ทับซ้อนน้อย/ไม่แน่ใจ) ให้เลือก **new** สร้างแยกต่างหาก เพราะ new เป็นทางเลือกที่ reversible กว่า (ย้าย/รวมทีหลังได้ง่าย) ในขณะที่ update ผิดอาจทำให้เนื้อหาที่ดีอยู่แล้วเสียหาย — บันทึกการตัดสินใจนี้เป็นหนึ่งในสมมติฐานสำคัญ
- **`missingInfo` อื่นๆ** (เช่น ค่าตัวเลขเกณฑ์ที่ spec ยังไม่ระบุ, รายละเอียดที่ spec กำกวม): เลือกสมมติฐานที่ใกล้เคียงบริบทของ spec ที่สุด (ไม่ใช่ค่ากลางทื่อๆ) แล้วทำงานต่อ ถ้าเป็นเนื้อหาที่ลงในเอกสารจริง ให้ทำเครื่องหมายสั้นๆ ในเอกสารด้วย `_(สมมติฐาน: ...)_` เพื่อให้ตรวจสอบย้อนหลังได้ง่าย
- **คะแนนในแผนภาพ mermaid journey**: ให้เป็นไปตามที่ subagent `journey-designer` ประเมินเอง (ดูเกณฑ์ในตัว subagent) ไม่ต้องให้ผู้ใช้กรอก

ข้อยกเว้นเดียวที่ยังต้องหยุดถามผู้ใช้ด้วย AskUserQuestion (บังคับ ≥3 ตัวเลือกเสมอ ไม่นับ "Other"): งานติดขัดจนทำต่อไม่ได้จริงๆ เช่น path spec ที่ผู้ใช้ระบุไม่มีอยู่จริง — ไม่ใช่กรณี "ความไม่ชัดเจนที่พอจะตั้งสมมติฐานได้" ตามด้านบน

## ขั้นตอนที่ 4 — สรุปการตัดสินใจ new/update/duplicate

ใช้ผลจาก subagent + การตัดสินใจตามกฎ default ในขั้นตอนที่ 3 (ถ้ามี) เพื่อสรุปเป็นการตัดสินใจสุดท้าย:

- **new**: ไปสร้างไฟล์ใหม่ตามขั้นตอนที่ 5 ตามปกติ
- **update**: แก้ไขไฟล์ features list และ/หรือ user journey เดิม (ตามที่ระบุใน `existingDocs`) โดยตรง — เอกสารออกแบบไม่ใช่เอกสารที่ approved-then-frozen แบบ requirement จึง update ตรงๆ ได้ ไม่ต้องย้ายไป `00-archived`
- **duplicate**: อย่าสร้าง/แก้ไฟล์ แจ้งผู้ใช้ว่ามีเอกสาร `{path}` ที่ครอบคลุมเรื่องนี้อยู่แล้ว พร้อมสรุปเนื้อหาเอกสารนั้นให้ แล้วจบ flow (ข้ามขั้นตอนที่ 5-6)

## ขั้นตอนที่ 5 — สร้าง/อัปเดตเอกสาร features list และ user journey

1. หาวันที่ปัจจุบันในรูปแบบ `YYYYMMDD`
2. หา `RUNNING_NO`: ใช้ Glob ดูไฟล์ที่มีอยู่แล้วใน `docs/02-design/01-prototypes/` ที่ขึ้นต้นด้วย `YYYYMMDD-` ของวันนี้ นับจำนวน แล้ว +1 ได้เลขลำดับถัดไป zero-pad เป็น 2 หลัก (running number นับรวมทุกไฟล์ในโฟลเดอร์นี้ ไม่แยกนับ features-list กับ user-journey)
3. สรุปหัวข้อเป็น `SUMMARIZE_TOPIC` แบบ kebab-case ภาษาอังกฤษสั้นๆ (3-6 คำ, a-z0-9 กับ `-` เท่านั้น) ที่สื่อความหมายของ spec ต้นทาง
4. เขียน/แก้ไขไฟล์:
   - `docs/02-design/01-prototypes/{YYYYMMDD}-{RUNNING_NO}-features-list-{SUMMARIZE_TOPIC}.md` — ใช้ `featuresListMarkdown` จาก subagent (ปรับตามสมมติฐานที่ตัดสินใจไว้ในขั้นตอนที่ 3 แล้ว) เป็นเนื้อหา
   - สำหรับแต่ละรายการใน `journeyMarkdown[]`: `docs/02-design/01-prototypes/{YYYYMMDD}-{RUNNING_NO}-user-journey-{persona-kebab}-{SUMMARIZE_TOPIC}.md` (running number เพิ่มทีละ 1 ต่อไฟล์) — ก่อนเขียนไฟล์ ตรวจว่าลิงก์ `[[./{ชื่อไฟล์ features list}|Features List]]` ในเนื้อหาตรงกับชื่อไฟล์ features list จริงที่เพิ่งกำหนดในข้อ 4 (แก้ placeholder ให้ตรง)
5. เพิ่ม wikilink กลับไปยังไฟล์ spec ต้นทาง (บรรทัดท้ายไฟล์ spec เดิม เช่น `> ดูฟีเจอร์และ journey ที่ derive จากเอกสารนี้: [[../../02-design/01-prototypes/{features-list-filename}|Features List]], [[../../02-design/01-prototypes/{user-journey-filename}|User Journey: {persona}]]`) — **ห้ามแก้เนื้อหาเดิมของ spec นอกจากเพิ่มลิงก์นี้**
6. เพิ่ม wikilink ไปยังไฟล์ใหม่ทั้งหมดใน `docs/02-design/01-prototypes/index.md` (เพิ่มเป็นรายการ bullet ต่อท้ายเนื้อหาที่มีอยู่ อย่าลบของเดิม)

## ขั้นตอนที่ 6 — บันทึก log ประจำวัน

เปิด (หรือสร้างถ้ายังไม่มี) `docs/05-log/{YYYYMMDD}-log.md` — ถ้าเพิ่งสร้างไฟล์ใหม่ ใส่หัวเรื่อง `# Log {YYYY-MM-DD}` ก่อน แล้วต่อท้ายไฟล์ (ไม่เขียนทับของเดิม) ด้วยรายการสรุปสิ่งที่ทำในรอบนี้ เช่น:

```markdown
## {HH:MM}
- สร้าง features list: [[../02-design/01-prototypes/{filename}|{หัวข้อ}]] จาก [[../01-requirements/01-spec/{spec-filename}|{หัวข้อ spec}]]
- สร้าง user journey: [[../02-design/01-prototypes/{filename}|{persona}: {เป้าหมาย}]]
- {ถ้ามี} อัปเดต {เอกสารเดิม} เนื่องจาก spec มีการเปลี่ยนแปลง
```

ถ้าไม่ทราบเวลาปัจจุบันแน่นอน ใช้หัวข้อย่อยเป็นลำดับเหตุการณ์แทนเวลาก็ได้ ถ้าไฟล์ของวันนี้มี `index.md` ที่ยังไม่ได้ลิงก์ไปวันที่นี้ ให้เพิ่มลิงก์จาก `docs/05-log/index.md` ด้วยเช่นกัน

## ขั้นตอนที่ 7 — สรุปให้ผู้ใช้

ถ้าขั้นตอนที่ 1 ให้ทำหลายฉบับ ให้ทำขั้นตอนนี้ **ครั้งเดียวหลังทำครบทุกฉบับแล้ว** เป็นสรุปรวมทุก topic ในคำตอบเดียว ไม่ใช่สรุปแยกทีละฉบับระหว่างทาง

เนื้อหาที่ต้องมี:

1. ต่อแต่ละ spec doc/topic ที่ทำ: สร้าง/แก้ไขไฟล์อะไรบ้าง (ลิงก์ markdown แบบ `[label](path)` ไม่ใช่ wikilink เพราะเป็นการรายงานในแชท ไม่ใช่เนื้อหาเอกสาร), ผลการวิเคราะห์ new/update/duplicate และเหตุผล, จำนวน journey ที่สร้างและ persona ของแต่ละอัน
2. **ข้อสันนิษฐานสำคัญที่ subagent/skill ใช้** — bullet list สั้นๆ รวบรวมจากทุก topic ที่ทำในรอบนี้ (เช่น การเลือก new/update ตอน `relationship: ambiguous`, ค่าที่สมมติขึ้นแทนข้อมูลที่ spec ไม่ระบุ, คะแนนในแผนภาพที่เป็นการประเมินเองของ subagent) ถ้าไม่มีสมมติฐานใดเลย ให้ระบุว่าไม่มี
3. **จุดที่ควรพิจารณาเปิด requirement เพิ่มเติม** — bullet list สั้นๆ ถ้ามี (เช่น business rule ที่ spec เว้นว่างไว้ชัดเจน, edge case ที่ยังไม่มี requirement รองรับ, ค่าตัวเลขเกณฑ์ที่ยังต้องยืนยันจริงก่อนขึ้นระบบจริง) ถ้าไม่มี ให้ระบุว่าไม่มี
