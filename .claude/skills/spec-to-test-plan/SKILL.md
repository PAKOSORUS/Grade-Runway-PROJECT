Skill นี้ทำหน้าที่รับ **Requirement, Backlog, Feature List และ User Journey ของหัวข้อหนึ่ง** (ทั้งหมด หรือเฉพาะที่ผู้ใช้ระบุ) แล้วดำเนินการทั้งหมดต่อไปนี้ให้ครบ: สร้าง/อัปเดตเอกสาร Acceptance Criteria, สร้าง/อัปเดตเอกสาร Test Plan (รวม test case table), อัปเดต index, และบันทึก log ประจำวัน โดยอ้างอิงธรรมเนียมของ vault ตามที่ระบุใน [CLAUDE.md](../../../CLAUDE.md) ที่ root ของ repo (ภาษาไทย, wikilink, ห้ามลบเอกสาร ฯลฯ)

ทำตามขั้นตอนนี้ตามลำดับ **ห้ามข้ามขั้นตอนใด**:

## ขั้นตอนที่ 1 — กำหนดขอบเขตเอกสารต้นทาง

1. หาว่าหัวข้อ (topic) ที่ผู้ใช้ต้องการวางแผนทดสอบคือเรื่องไหน:
   - ถ้าผู้ใช้ระบุชัดเจน (ชื่อ requirement, path ไฟล์, หรือ wikilink) ใช้ตามนั้นได้เลย
   - ถ้าไม่ระบุ ให้ Glob `docs/01-requirements/01-spec/*.md` (ไม่นับ `index.md`): พบไฟล์เดียว → ใช้ไฟล์นั้น, ไม่พบไฟล์เลย → แจ้งผู้ใช้ว่ายังไม่มีเอกสาร requirement ในโปรเจกต์แล้วหยุด, พบมากกว่าหนึ่ง → **default เป็น "ทำทั้งหมด" โดยไม่ต้องถามยืนยัน** วนทำทีละฉบับให้ครบขั้นตอนที่ 2–6 (วิเคราะห์ → ตัดสินใจ → สร้าง/แก้ไฟล์ → บันทึก log) จนจบก่อนขึ้นฉบับถัดไปเสมอ — **ห้ามทำหลายฉบับพร้อมกัน** เพราะการนับ `RUNNING_NO` ในขั้นตอนที่ 5 และการ append เข้าไฟล์ log วันเดียวกันในขั้นตอนที่ 6 ต้องอ่านสถานะล่าสุดของไฟล์ก่อนเขียนทุกครั้ง ทำครบทุกฉบับแล้วค่อยไปขั้นตอนที่ 7 เพื่อสรุปรวมทุก topic ในคำตอบเดียว
2. เมื่อได้ spec เป้าหมายแล้ว ใช้ Grep หา wikilink ที่ชี้กลับไปยัง spec นี้ เพื่อรวบรวมเอกสารที่เกี่ยวข้องอีกสามประเภท: แถวใน `docs/01-requirements/backlog.md`, ไฟล์ features-list และไฟล์ user-journey (ทุกฉบับ ทุก persona) ใน `docs/02-design/01-prototypes/`
3. **ค่าเริ่มต้นคือใช้ทั้งหมดที่พบ** เว้นแต่ผู้ใช้ระบุเจาะจงว่าต้องการใช้เฉพาะบางเอกสาร (เช่น "ใช้แค่ spec กับ feature list ไม่ต้องดู user journey") — ถ้าระบุเจาะจงมา ให้ตัดเอกสารประเภทอื่นออกจาก input ที่จะส่งให้ subagent ในขั้นตอนที่ 2
4. ถ้าพบว่ายังไม่เคยมี features-list หรือ user-journey ที่ derive จาก spec นี้เลย (เช่น ยังไม่เคยรัน `/spec-to-journey`) **ไม่ต้องหยุดถามผู้ใช้** — ทำ test plan ต่อด้วยข้อมูลเท่าที่มี (spec ± backlog) ได้เลย โดยบันทึกไว้เป็นหนึ่งใน "ข้อสันนิษฐานสำคัญ" ที่จะรายงานตอนจบว่า Acceptance Criteria/Test Plan ชุดนี้อาจหยาบกว่าปกติเพราะยังไม่มี feature-list/user-journey ให้ traceability ครบ

## ขั้นตอนที่ 2 — วิเคราะห์และร่างเนื้อหาโดย subagent

เรียก subagent ชื่อ `test-designer` (ผ่าน Agent tool, `run_in_background: false` เพราะต้องใช้ผลลัพธ์ทันทีในขั้นตอนถัดไป) โดยส่ง path เอกสารต้นทางทั้งหมดที่สรุปได้จากขั้นตอนที่ 1 (เท่าที่มี/เท่าที่ผู้ใช้ระบุ) ให้ subagent วิเคราะห์ว่ามีเอกสารทดสอบเดิมที่ derive จาก spec นี้อยู่แล้วหรือไม่ (`new` / `update` / `duplicate` / `ambiguous`) พร้อมร่าง `acceptanceCriteriaMarkdown` + `testPlanMarkdown` กลับมาด้วย

## ขั้นตอนที่ 3 — ตัดสินใจเองเมื่อข้อมูลไม่ชัดเจน

หลักการ: **ตัดสินใจเองแล้วทำงานต่อให้เสร็จ ห้ามหยุดถามผู้ใช้ระหว่างทาง** ใช้สมมติฐานที่สมเหตุสมผลที่สุดจากบริบทของ spec/feature-list/user-journey เอง แล้วจดบันทึกทุกสมมติฐานสำคัญที่ใช้ไว้ (สะสมไว้ข้ามทุก spec doc ที่ทำในรอบนี้) เพื่อรายงานรวมให้ผู้ใช้ทราบในขั้นตอนที่ 7

แนวทางตัดสินใจสำหรับกรณีที่พบบ่อย:

- **`relationship: ambiguous`** (พบเอกสารทดสอบเดิมที่เกี่ยวข้องแต่ subagent ไม่มั่นใจว่าควร update หรือสร้างใหม่): ใช้กฎ default นี้ — ถ้าเอกสารเดิมที่พบ derive จาก spec เดียวกันและเนื้อหาทับซ้อนกับ spec/feature-list/user-journey ปัจจุบันเกินครึ่ง ให้เลือก **update** เอกสารนั้นตรงๆ มิฉะนั้น (ทับซ้อนน้อย/ไม่แน่ใจ) ให้เลือก **new** สร้างแยกต่างหาก เพราะ new เป็นทางเลือกที่ reversible กว่า — บันทึกการตัดสินใจนี้เป็นหนึ่งในสมมติฐานสำคัญ
- **`relationship: update` ที่มีเพียงไฟล์เดียว** (พบแค่ Acceptance Criteria เดิม หรือแค่ Test Plan เดิม ไม่ครบคู่): ไฟล์ที่ขาดไปให้สร้างเป็นไฟล์ใหม่ (running number ถัดไป) ที่อ้างอิงไฟล์เดิมที่มีอยู่แล้ว ไม่ต้องถามผู้ใช้
- **Priority ของ test case ที่ไม่มี feature-list รองรับ**: ยึดตามที่ subagent ประเมินจาก business rule ของ spec เอง (ดูเกณฑ์ในตัว subagent)
- **`missingInfo` อื่นๆ** (เช่น ค่าตัวเลขเกณฑ์ที่ spec ยังไม่ระบุ, test data ที่ยังไม่ชัดเจน): เลือกสมมติฐานที่ใกล้เคียงบริบทของ spec ที่สุด (ไม่ใช่ค่ากลางทื่อๆ) แล้วทำงานต่อ ถ้าเป็นเนื้อหาที่ลงในเอกสารจริง ให้ทำเครื่องหมายสั้นๆ ในเอกสารด้วย `_(สมมติฐาน: ...)_` เพื่อให้ตรวจสอบย้อนหลังได้ง่าย

ข้อยกเว้นเดียวที่ยังต้องหยุดถามผู้ใช้ด้วย AskUserQuestion (บังคับ ≥3 ตัวเลือกเสมอ ไม่นับ "Other"): งานติดขัดจนทำต่อไม่ได้จริงๆ เช่น path spec ที่ผู้ใช้ระบุไม่มีอยู่จริง — ไม่ใช่กรณี "ความไม่ชัดเจนที่พอจะตั้งสมมติฐานได้" ตามด้านบน

## ขั้นตอนที่ 4 — สรุปการตัดสินใจ new/update/duplicate

ใช้ผลจาก subagent + การตัดสินใจตามกฎ default ในขั้นตอนที่ 3 (ถ้ามี) เพื่อสรุปเป็นการตัดสินใจสุดท้าย:

- **new**: ไปสร้างไฟล์ใหม่ตามขั้นตอนที่ 5 ตามปกติ
- **update**: แก้ไขไฟล์ Acceptance Criteria และ/หรือ Test Plan เดิม (ตามที่ระบุใน `existingDocs`) โดยตรง — เอกสารทดสอบไม่ใช่เอกสารที่ approved-then-frozen แบบ requirement จึง update ตรงๆ ได้ ไม่ต้อง archive
- **duplicate**: อย่าสร้าง/แก้ไฟล์ แจ้งผู้ใช้ว่ามีเอกสาร `{path}` ที่ครอบคลุมเรื่องนี้อยู่แล้ว พร้อมสรุปเนื้อหาเอกสารนั้นให้ แล้วจบ flow (ข้ามขั้นตอนที่ 5-6)

## ขั้นตอนที่ 5 — สร้าง/อัปเดตเอกสาร Acceptance Criteria และ Test Plan

1. หาวันที่ปัจจุบันในรูปแบบ `YYYYMMDD`
2. หา `RUNNING_NO`: ใช้ Glob ดูไฟล์ที่มีอยู่แล้วใน `docs/03-testing/01-test-plan/` ที่ขึ้นต้นด้วย `YYYYMMDD-` ของวันนี้ นับจำนวน แล้ว +1 ได้เลขลำดับถัดไป zero-pad เป็น 2 หลัก (running number นับรวมทุกไฟล์ในโฟลเดอร์นี้ ไม่แยกนับ acceptance-criteria กับ test-plan)
3. สรุปหัวข้อเป็น `SUMMARIZE_TOPIC` แบบ kebab-case ภาษาอังกฤษสั้นๆ (3-6 คำ, a-z0-9 กับ `-` เท่านั้น) ที่สื่อความหมายของ spec ต้นทาง
4. เขียน/แก้ไขไฟล์:
   - `docs/03-testing/01-test-plan/{YYYYMMDD}-{RUNNING_NO}-acceptance-criteria-{SUMMARIZE_TOPIC}.md` — ใช้ `acceptanceCriteriaMarkdown` จาก subagent (ปรับตามสมมติฐานที่ตัดสินใจไว้ในขั้นตอนที่ 3 แล้ว) เป็นเนื้อหา (ข้ามไฟล์นี้ถ้า subagent ส่งกลับมาว่างเพราะเดิมครอบคลุมครบแล้ว)
   - `docs/03-testing/01-test-plan/{YYYYMMDD}-{RUNNING_NO}-test-plan-{SUMMARIZE_TOPIC}.md` (running number เพิ่มทีละ 1 ถ้าเขียนต่อจากไฟล์ acceptance criteria ในรอบเดียวกัน) — ใช้ `testPlanMarkdown` จาก subagent เป็นเนื้อหา ก่อนเขียนไฟล์ ตรวจว่าลิงก์ `[[./{ชื่อไฟล์ acceptance criteria}|Acceptance Criteria]]` ตรงกับชื่อไฟล์จริงที่เพิ่งกำหนด (แก้ placeholder ให้ตรง)
5. เพิ่ม wikilink กลับไปยังไฟล์ spec ต้นทาง (บรรทัดท้ายไฟล์ spec เดิม เช่น `> ดู test plan ที่ derive จากเอกสารนี้: [[../../03-testing/01-test-plan/{acceptance-criteria-filename}|Acceptance Criteria]], [[../../03-testing/01-test-plan/{test-plan-filename}|Test Plan]]`) — **ห้ามแก้เนื้อหาเดิมของ spec นอกจากเพิ่มลิงก์นี้** และห้ามเพิ่มซ้ำถ้ามีลิงก์นี้อยู่แล้ว (กรณี update ที่เคยเพิ่มไปแล้วในรอบก่อน)
6. เพิ่ม wikilink ไปยังไฟล์ใหม่ทั้งหมดใน `docs/03-testing/01-test-plan/index.md` (เพิ่มเป็นรายการ bullet ต่อท้ายเนื้อหาที่มีอยู่ ในหัวข้อ `## เอกสาร` — สร้างหัวข้อนี้ใหม่ถ้ายังไม่มี อย่าลบของเดิม)

## ขั้นตอนที่ 6 — บันทึก log ประจำวัน

เปิด (หรือสร้างถ้ายังไม่มี) `docs/05-log/{YYYYMMDD}-log.md` — ถ้าเพิ่งสร้างไฟล์ใหม่ ใส่หัวเรื่อง `# Log {YYYY-MM-DD}` ก่อน แล้วต่อท้ายไฟล์ (ไม่เขียนทับของเดิม) ด้วยรายการสรุปสิ่งที่ทำในรอบนี้ เช่น:

```markdown
## {HH:MM}
- สร้าง Acceptance Criteria: [[../03-testing/01-test-plan/{filename}|{หัวข้อ}]] จาก [[../01-requirements/01-spec/{spec-filename}|{หัวข้อ spec}]]
- สร้าง Test Plan: [[../03-testing/01-test-plan/{filename}|{หัวข้อ}]] ({จำนวน} test case)
- {ถ้ามี} อัปเดต {เอกสารเดิม} เนื่องจาก spec/feature-list/user-journey มีการเปลี่ยนแปลง
```

ถ้าไม่ทราบเวลาปัจจุบันแน่นอน ใช้หัวข้อย่อยเป็นลำดับเหตุการณ์แทนเวลาก็ได้ ถ้าไฟล์ของวันนี้มี `index.md` ที่ยังไม่ได้ลิงก์ไปวันที่นี้ ให้เพิ่มลิงก์จาก `docs/05-log/index.md` ด้วยเช่นกัน

## ขั้นตอนที่ 7 — สรุปให้ผู้ใช้

ถ้าขั้นตอนที่ 1 ให้ทำหลายฉบับ ให้ทำขั้นตอนนี้ **ครั้งเดียวหลังทำครบทุกฉบับแล้ว** เป็นสรุปรวมทุก topic ในคำตอบเดียว ไม่ใช่สรุปแยกทีละฉบับระหว่างทาง

เนื้อหาที่ต้องมี:

1. ต่อแต่ละ spec doc/topic ที่ทำ: สร้าง/แก้ไขไฟล์อะไรบ้าง (ลิงก์ markdown แบบ `[label](path)` ไม่ใช่ wikilink เพราะเป็นการรายงานในแชท ไม่ใช่เนื้อหาเอกสาร), ผลการวิเคราะห์ new/update/duplicate และเหตุผล, จำนวน AC และจำนวน test case ที่สร้าง
2. **ข้อสันนิษฐานสำคัญที่ subagent/skill ใช้** — bullet list สั้นๆ รวบรวมจากทุก topic ที่ทำในรอบนี้ (เช่น การเลือก new/update ตอน `relationship: ambiguous`, กรณีที่ทำโดยไม่มี feature-list/user-journey รองรับครบ, ค่า test data/priority ที่สมมติขึ้นแทนข้อมูลที่ spec ไม่ระบุ) ถ้าไม่มีสมมติฐานใดเลย ให้ระบุว่าไม่มี
3. **จุดที่ควรพิจารณาเพิ่มเติม** — bullet list สั้นๆ ถ้ามี (เช่น business rule ที่ spec เว้นว่างไว้ชัดเจนจนกระทบ test case, edge case ที่ยังไม่มี user journey รองรับ, ค่าตัวเลขเกณฑ์ที่ยังต้องยืนยันจริงก่อนขึ้นระบบจริง) ถ้าไม่มี ให้ระบุว่าไม่มี
