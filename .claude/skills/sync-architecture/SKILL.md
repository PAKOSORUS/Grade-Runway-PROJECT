Skill นี้ทำหน้าที่สร้างหรือปรับปรุง **เอกสาร high level architecture แบบ conceptual** ฉบับเดียว (living document) ที่ `docs/02-design/02-technical/high-level-architecture.md` ให้สอดคล้องกับ requirement และ user journey ล่าสุดใน vault โดยไม่ระบุ technical stack ทำตามธรรมเนียมใน [CLAUDE.md](../../../CLAUDE.md) ที่ root ของ repo (ภาษาไทย, wikilink, ห้ามลบเอกสาร ฯลฯ)

> **หมายเหตุเรื่อง path:** โครงสร้างจริงของ vault ใช้ `docs/02-design/02-technical/` (ไม่ใช่ `docs/design/`) เพื่อรักษาห่วงโซ่ requirements → design → testing ตาม CLAUDE.md ให้ใช้ path นี้เสมอ

ต่างจาก skill อื่นในโปรเจกต์ที่ "ตัดสินใจเองไม่ถามระหว่างทาง" skill นี้ **ต้องถามผู้ใช้เมื่อพบความไม่ชัดเจนที่กระทบรูปทรง architecture** (ดูขั้นตอนที่ 3) เพราะการตัดสินใจเชิงสถาปัตยกรรมผิดทางส่งผลลามไปถึงงานทุกอย่างถัดไป

ทำตามขั้นตอนตามลำดับ **ห้ามข้ามขั้นตอนใด**:

## ขั้นตอนที่ 1 — กำหนดขอบเขต

ถ้าผู้ใช้ระบุ spec/topic ไว้ชัดเจน ให้ใช้เฉพาะที่ระบุ ถ้าไม่ระบุ ให้ใช้ **ทุก spec** ใน `docs/01-requirements/01-spec/*.md` (ไม่นับ `index.md`) ที่ไม่ใช่สถานะ `Superseded` ใน `docs/01-requirements/backlog.md` — เอกสารนี้เป็นภาพรวมของทั้งระบบ จึง default เป็นทั้งหมด

- ไม่พบ spec เลย → แจ้งผู้ใช้ว่ายังไม่มี requirement ให้วิเคราะห์ แนะนำให้รัน `/requirement-to-backlog` ก่อน แล้วหยุด
- พบ spec แต่ยังไม่มี user journey ของ spec ใดเลย → ทำต่อได้ (subagent จะใช้ User Stories แทน) แต่ต้องแจ้งในสรุปท้ายว่าควรรัน `/spec-to-journey` ก่อนเพื่อให้ data flow แม่นยำขึ้น

## ขั้นตอนที่ 2 — วิเคราะห์และร่างเนื้อหา

เรียก subagent ชื่อ `architecture-writer` (ผ่าน Agent tool, `run_in_background: false`) ส่งรายการ path ของ spec ในขอบเขต และ path ของเอกสาร architecture เดิมถ้ามี (ตรวจด้วย Glob ที่ `docs/02-design/02-technical/high-level-architecture.md`) ให้ subagent คืน `relationship`, `coverage`, `openQuestions`, `assumptions`, `changeSummary` และ `architectureMarkdown`

## ขั้นตอนที่ 3 — ถามผู้ใช้เมื่อมีจุดไม่ชัดเจน

ถ้า `openQuestions` ว่าง ข้ามไปขั้นตอนที่ 4

ถ้ามี ให้ถามผู้ใช้ด้วย AskUserQuestion โดยปฏิบัติตามนี้:

- ถามทีละไม่เกิน 4 คำถามต่อครั้ง เรียงตามลำดับความสำคัญที่ subagent จัดมา ถ้ามีเกิน 4 ให้ถามรอบละ 4 ต่อเนื่องกันจนครบ
- **ทุกคำถามต้องมีตัวเลือกจริงอย่างน้อย 3 ข้อ** (ไม่นับ "Other" ที่ระบบเติมให้) ถ้า subagent ส่งมาน้อยกว่า 3 ข้อ ให้เติมทางเลือกที่สมเหตุสมผลเองจนครบ ห้ามถามด้วยตัวเลือกไม่ถึง 3 ข้อ
- ใน `description` ของแต่ละตัวเลือกให้ใส่ **ข้อดี** และ **ข้อเสีย** ที่เฉพาะเจาะจงกับ Grade Runway รูปแบบ `ดี: … | เสีย: …`
- ตัวเลือกที่ subagent แนะนำวางเป็นข้อแรก และต่อท้าย label ด้วย `(Recommended)`
- `header` สั้นไม่เกิน 12 ตัวอักษร ตัวเลือกยังต้องเป็นระดับ conceptual ไม่ใช่การเลือกเทคโนโลยี
- ถ้าผู้ใช้ตอบ "Other" ให้ตีความคำตอบนั้นเป็นการตัดสินใจและใช้ตามนั้น ถ้าคลุมเครือถึงขั้นตีความไม่ได้ให้ถามซ้ำเฉพาะข้อนั้นอีกครั้ง
- ถ้าผู้ใช้ปฏิเสธที่จะตอบข้อใด ให้ใช้ `fallbackAssumption` ของข้อนั้นและบันทึกเป็นสมมติฐาน

เมื่อได้คำตอบครบ ให้เรียก subagent `architecture-writer` **อีกครั้ง** พร้อมแนบคำตอบทั้งหมดเป็นการตัดสินใจที่ยืนยันแล้ว เพื่อให้ได้ `architectureMarkdown` ฉบับที่สะท้อนคำตอบ (ถ้าคำตอบทำให้เกิดคำถามใหม่ที่สำคัญจริงให้วนถามได้ แต่ไม่เกิน 2 รอบรวม เพื่อไม่ให้ผู้ใช้เหนื่อย — ที่เหลือใช้ fallback assumption)

## ขั้นตอนที่ 4 — สรุปการตัดสินใจ new/update/up-to-date

- **new**: สร้างไฟล์ใหม่ในขั้นตอนที่ 5
- **update**: แก้ไขไฟล์เดิมโดยตรง (เอกสารนี้เป็น living document ไม่ต้องย้ายไป `00-archived`) แต่ถ้ามีเนื้อหาเดิมที่ถูกแทนที่ด้วยการตัดสินใจใหม่อย่างมีนัยสำคัญ ให้คงร่องรอยไว้ในหัวข้อ "การตัดสินใจเชิงสถาปัตยกรรมที่ยืนยันแล้ว" (ใส่วันที่และสิ่งที่เปลี่ยน) เพื่อรักษาประวัติการตัดสินใจ
- **up-to-date**: ห้ามแก้ไฟล์ แจ้งผู้ใช้ว่าเอกสารเดิมครอบคลุมแล้วพร้อมสรุปสั้นๆ แล้วจบ flow (ข้ามขั้นตอนที่ 5-7) ยกเว้นผู้ใช้ตอบคำถามที่ทำให้การตัดสินใจเปลี่ยน ซึ่งจะทำให้กลายเป็น `update`

## ขั้นตอนที่ 5 — เขียนเอกสาร

1. หาวันที่ปัจจุบัน `YYYY-MM-DD` ใส่ในบรรทัด "อัปเดตล่าสุด" และคอลัมน์วันที่ของการตัดสินใจ
2. ตรวจ `architectureMarkdown` ก่อนเขียนไฟล์:
   - wikilink ทุกอันชี้ไปยังไฟล์ที่มีอยู่จริง (ตรวจด้วย Glob) path สัมพัทธ์จาก `docs/02-design/02-technical/`
   - ไม่มีชื่อเทคโนโลยี/ผลิตภัณฑ์/framework ปนอยู่ในแผนภาพหรือเนื้อหาหลัก (ยกเว้นหัวข้อ "ข้อจำกัดจาก Requirement") ถ้าพบให้แทนด้วยคำกลาง
   - Mermaid แต่ละบล็อกมี syntax ที่ถูกต้อง (node id เป็นอังกฤษ, label ภาษาไทยที่มีอักขระพิเศษครอบด้วย `"..."`)
   - หัวข้อ "การตัดสินใจเชิงสถาปัตยกรรมที่ยืนยันแล้ว" มีคำตอบของผู้ใช้ครบทุกข้อ และหัวข้อ "คำถามค้างและสมมติฐาน" มีเฉพาะสิ่งที่ยังไม่ได้ยืนยัน
3. เขียนไฟล์ `docs/02-design/02-technical/high-level-architecture.md` (ใช้ชื่อไฟล์คงที่นี้เสมอ ไม่มีเลข running number เพราะเป็นเอกสารเดียวที่ปรับปรุงต่อเนื่อง)
4. เพิ่ม wikilink ไปยังเอกสารใน `docs/02-design/02-technical/index.md` เป็น bullet (ถ้ายังไม่มี ห้ามลบเนื้อหาเดิม) เช่น `- [[high-level-architecture|High Level Architecture (Conceptual)]] — ภาพรวมระบบเชิงแนวคิด ยังไม่ผูกกับ technical stack`
5. เพิ่มลิงก์ย้อนกลับท้ายไฟล์ spec แต่ละฉบับในขอบเขต **ถ้ายังไม่มี** (เพิ่มบรรทัดเดียว เช่น `> ภาพรวมสถาปัตยกรรมที่เกี่ยวข้อง: [[../../02-design/02-technical/high-level-architecture|High Level Architecture]]`) **ห้ามแก้เนื้อหาเดิมของ spec นอกจากเพิ่มลิงก์นี้**

## ขั้นตอนที่ 6 — backlog

skill นี้ **ไม่เปลี่ยนสถานะใน `docs/01-requirements/backlog.md`** เพราะ architecture เป็นเอกสารภาพรวมข้ามหลาย requirement ไม่ใช่ผลลัพธ์ของ requirement ใด requirement หนึ่ง ข้ามขั้นตอนนี้ และห้ามแตะ backlog

## ขั้นตอนที่ 7 — บันทึก log ประจำวัน

เปิด (หรือสร้างถ้ายังไม่มี) `docs/05-log/{YYYYMMDD}-log.md` — ถ้าเพิ่งสร้างใหม่ใส่หัวเรื่อง `# Log {YYYY-MM-DD}` ก่อน แล้วต่อท้ายไฟล์ (ไม่เขียนทับ) ด้วย:

```markdown
## {HH:MM}
- {สร้าง|อัปเดต} high level architecture: [[../02-design/02-technical/high-level-architecture|High Level Architecture]] จาก spec {จำนวน} ฉบับ
- ตัดสินใจเชิงสถาปัตยกรรมร่วมกับผู้ใช้: {หัวข้อ → ตัวเลือกที่เลือก} (หนึ่งบรรทัดต่อข้อ ถ้ามี)
- {ถ้า update} สิ่งที่เปลี่ยน: {สรุปจาก changeSummary}
```

ถ้าไม่ทราบเวลาแน่นอนใช้ลำดับเหตุการณ์แทนได้ ถ้า `docs/05-log/index.md` ยังไม่ลิงก์วันที่นี้ ให้เพิ่มลิงก์ด้วย

## ขั้นตอนที่ 8 — สรุปให้ผู้ใช้

สรุปเป็นข้อความภาษาไทยในคำตอบเดียว ใช้ markdown link `[label](path)` (ไม่ใช่ wikilink) ประกอบด้วย:

1. ไฟล์ที่สร้าง/แก้ พร้อมผลการวิเคราะห์ new/update/up-to-date และ spec/journey ที่ครอบคลุม
2. **การตัดสินใจที่ผู้ใช้ยืนยันในรอบนี้** — ตารางสั้น หัวข้อ → ตัวเลือกที่เลือก
3. **ข้อสันนิษฐานที่ยังไม่ได้ยืนยัน** — bullet list (ถ้าไม่มีให้ระบุว่าไม่มี)
4. **สิ่งที่ควรทำต่อ** — เช่น spec ที่ยังไม่มี journey, ประเด็นที่ควรเปิด requirement เพิ่ม, หรือเมื่อพร้อมเลือก technical stack ให้สั่งทำเอกสารถัดไปแยกต่างหาก
