# Acceptance Criteria: ช่องแชทรีวิวและแนะนำวิธีการเรียนจากนักศึกษาเกรดสูง

## Acceptance Criteria ต่อ User Story

### AC-1: ระบบประมวลผลผลการเรียนและเสนอชื่อผู้แนะนำอัตโนมัติ
**อ้างอิง User Story:** "ในฐานะระบบ ฉันต้องการประมวลผลรายชื่อนักศึกษาที่เข้าเกณฑ์ผลการเรียนสูงในแต่ละวิชา แล้วเสนอชื่อ (suggest) ให้ผู้ดูแลระบบพิจารณาอนุมัติเป็นผู้แนะนำ/ผู้รีวิวประจำห้องแชทนั้น" (US3, อ้าง Business Rule ข้อ 1 ข้อย่อย 1)

- **Given** นักศึกษาคนหนึ่งลงทะเบียนเรียนวิชา X ในภาคการศึกษาปัจจุบัน และผลการเรียน (เกรดวิชา/GPA สะสม) ของนักศึกษาคนนั้นเข้าเกณฑ์ที่ตั้งค่าไว้สำหรับวิชา X
- **When** ระบบประมวลผลผลการเรียนตามรอบที่กำหนด
- **Then** ระบบต้องเพิ่มชื่อนักศึกษาคนนั้นเข้าคิว "รายชื่อที่ระบบเสนอ" ของวิชา X เพื่อรอแอดมินพิจารณา โดยยังไม่ให้สิทธิ์ผู้แนะนำทันที (Business Rule: ระบบจะไม่ให้สิทธิ์อัตโนมัติทันทีที่เข้าเกณฑ์เกรด)
- **Given** เกณฑ์ผลการเรียนของวิชา X เป็นค่า configurable ที่แอดมินตั้งค่าได้ — **When** แอดมินเปลี่ยนค่าเกณฑ์ — **Then** รอบประมวลผลถัดไปต้องใช้เกณฑ์ใหม่ที่ปรับแล้ว _(ต้องการข้อมูลเพิ่มเติมจากผู้ใช้: ค่าตัวเลขเกณฑ์เริ่มต้นและความถี่ของรอบประมวลผล)_
- **Given** นักศึกษาผลการเรียนไม่เข้าเกณฑ์ของวิชา X — **When** ระบบประมวลผล — **Then** ต้องไม่ถูกเสนอชื่อเข้าคิวของวิชา X

### AC-2: แอดมินตรวจสอบและยืนยันความเหมาะสมของรายชื่อผู้แนะนำ (approve/reject)
**อ้างอิง User Story:** "ในฐานะผู้ดูแลระบบ ฉันต้องการตรวจสอบและยืนยันความเหมาะสม (approve) ของรายชื่อที่ระบบเสนอมา ก่อนที่นักศึกษาคนนั้นจะได้รับสิทธิ์เป็นผู้แนะนำในห้องแชท" (US4, อ้าง Business Rule ข้อ 1 ข้อย่อย 2)

- **Given** มีรายชื่อนักศึกษาที่ระบบเสนอรออยู่ในคิวอนุมัติของวิชา X
- **When** แอดมิน approve รายชื่อนักศึกษาคนหนึ่ง
- **Then** นักศึกษาคนนั้นต้องได้รับสิทธิ์บทบาทผู้แนะนำ/ผู้รีวิว (mentor role) ในห้องแชทของวิชา X และสามารถโพสต์ข้อความได้
- **Given** มีรายชื่อนักศึกษาที่ระบบเสนอรออยู่ในคิว — **When** แอดมิน reject รายชื่อนักศึกษาคนหนึ่ง — **Then** นักศึกษาคนนั้นต้องไม่ได้รับสิทธิ์ผู้แนะนำ และระบบต้องไม่ให้สิทธิ์อัตโนมัติแม้ผลการเรียนยังเข้าเกณฑ์
- **Given** นักศึกษาถูก reject ไปแล้ว — เหตุผลของการ reject และสิทธิ์ในการถูกเสนอชื่อ/ยื่นใหม่ในรอบถัดไป _(ต้องการข้อมูลเพิ่มเติมจากผู้ใช้ — อ้างอิง Edge Case ใน user journey ผู้แนะนำ: "ระบบเสนอชื่อแล้วแต่แอดมินไม่อนุมัติ ยังไม่ระบุว่ามีการแจ้งเหตุผลหรือให้ยื่นใหม่ได้หรือไม่")_
- **Given** นักศึกษาได้รับสิทธิ์ผู้แนะนำแล้ว แต่ภาคการศึกษาถัดไปผลการเรียนตกต่ำกว่าเกณฑ์ — การเพิกถอนสิทธิ์ผู้แนะนำ _(ต้องการข้อมูลเพิ่มเติมจากผู้ใช้ — spec ไม่ระบุกลไก revoke)_

### AC-3: ห้องแชทแยกตามรายวิชาและจำกัดสิทธิ์การเข้าถึงตามการลงทะเบียนภาคปัจจุบัน
**อ้างอิง User Story:** อ้าง Business Rule "ห้องแชทถูกจัดกลุ่มแยกตามรายวิชา" และ "ขอบเขตการเข้าถึงห้องแชทของแต่ละวิชา จำกัดเฉพาะนักศึกษาที่ลงทะเบียนเรียนวิชานั้นอยู่ในภาคการศึกษาปัจจุบัน" ประกอบ US1, US2

- **Given** นักศึกษาลงทะเบียนเรียนวิชา X ในภาคการศึกษาปัจจุบัน
- **When** นักศึกษาเปิดห้องแชทของวิชา X
- **Then** ระบบต้องอนุญาตให้เข้าห้องแชทได้ และเห็นเฉพาะห้องแชทของวิชาที่ตนลงทะเบียนอยู่เท่านั้น
- **Given** นักศึกษาไม่ได้ลงทะเบียนวิชา X ในภาคการศึกษาปัจจุบัน (เช่น เคยเรียนภาคก่อนหน้า หรือยังไม่ได้ลงทะเบียน) — **When** พยายามเข้าห้องแชทของวิชา X — **Then** ระบบต้องปฏิเสธการเข้าถึง
- **Given** นักศึกษาถอนวิชา X ระหว่างภาคการศึกษา — **When** ตรวจสอบสิทธิ์เข้าห้องแชทของวิชา X ภายหลัง — **Then** ต้องไม่สามารถเข้าถึงห้องแชทของวิชา X ได้อีก _(ต้องการข้อมูลเพิ่มเติมจากผู้ใช้ — spec ไม่ระบุว่ามีดีเลย์การตัดสิทธิ์หรือไม่ อ้างอิง Edge Case ใน user journey นักศึกษาทั่วไป)_

### AC-4: ผู้แนะนำโพสต์ข้อความ/คำแนะนำในห้องแชท (ต้องผ่าน pre-moderation ก่อนเผยแพร่)
**อ้างอิง User Story:** "ในฐานะนักศึกษาที่มีผลการเรียนสูง/ผ่านเกณฑ์ที่ระบบกำหนด ฉันต้องการเข้าไปแนะนำหรือรีวิววิธีการเรียนของฉันในห้องแชทของรายวิชาที่ฉันเรียนอยู่" (US1) ประกอบ Business Rule เรื่อง pre-moderation

- **Given** นักศึกษาได้รับสิทธิ์ผู้แนะนำในห้องแชทของวิชา X แล้ว (ผ่าน AC-2)
- **When** ผู้แนะนำพิมพ์และส่งข้อความแนะนำวิธีเรียนในห้องแชทของวิชา X
- **Then** ข้อความต้องถูกส่งเข้าคิว pre-moderation ก่อน และยังไม่แสดงให้นักศึกษาคนอื่นเห็นจนกว่าจะผ่านการตรวจสอบ (Business Rule: "ทุกข้อความ/โพสต์ในห้องแชทต้องผ่านการตรวจสอบก่อนเผยแพร่")
- **Given** ข้อความผ่านการตรวจสอบและถูก approve โดยผู้ดูแลระบบ — **When** การอนุมัติเสร็จสมบูรณ์ — **Then** ข้อความต้องแสดงในห้องแชทให้นักศึกษาคนอื่นในวิชานั้นเห็น
- **Given** ข้อความถูกผู้ดูแลระบบ reject — **Then** ข้อความต้องไม่ถูกเผยแพร่ และผู้โพสต์ควรได้รับแจ้งสถานะ _(ต้องการข้อมูลเพิ่มเติมจากผู้ใช้ — spec ไม่ระบุกลไกแจ้งผลเผยแพร่/ปฏิเสธให้ผู้โพสต์ทราบโดยตรง; สมมติฐานอ้างอิง features-list แถว 10 ว่าควรมีสถานะอย่างน้อย 3 แบบ คือ รอตรวจสอบ/เผยแพร่แล้ว/ถูกปฏิเสธ)_
- **Given** ผู้ใช้ที่ไม่มีสิทธิ์ผู้แนะนำในวิชา X (ยังไม่ผ่าน approve หรือไม่ได้ลงทะเบียนวิชานั้น) — **When** พยายามโพสต์ข้อความในบทบาทผู้แนะนำ — **Then** ระบบต้องปฏิเสธการโพสต์

### AC-5: นักศึกษาทั่วไปอ่านและตั้งคำถาม/ขอคำแนะนำในห้องแชท
**อ้างอิง User Story:** "ในฐานะนักศึกษาทั่วไป ฉันต้องการเข้าไปอ่าน/สนทนากับนักศึกษาที่ได้เกรดสูงในห้องแชทของรายวิชาที่ฉันเรียน เพื่อขอคำแนะนำแนวทางการเรียนที่ได้ผลจริงและตรงกับวิชานั้นๆ" (US2)

- **Given** นักศึกษาทั่วไปลงทะเบียนเรียนวิชา X ในภาคปัจจุบัน และอยู่ในห้องแชทของวิชา X
- **When** เปิดห้องแชท
- **Then** ต้องเห็นข้อความ/คำแนะนำทั้งหมดที่ผ่านการเผยแพร่แล้วของวิชา X
- **Given** นักศึกษาทั่วไปต้องการขอคำแนะนำ — **When** พิมพ์และส่งคำถามในห้องแชท — **Then** ข้อความคำถามต้องเข้าคิว pre-moderation ก่อนเผยแพร่เช่นเดียวกับข้อความของผู้แนะนำ (ตีความจาก Business Rule ที่ระบุว่า "ทุกข้อความ" ต้องผ่านการตรวจสอบ) _(ต้องการข้อมูลเพิ่มเติมจากผู้ใช้เพื่อยืนยันว่าคำถามของนักศึกษาทั่วไปต้องผ่าน pre-moderation เหมือนกันหรือมีข้อยกเว้น — user journey นักศึกษาทั่วไปให้คะแนนความมั่นใจต่ำในขั้นตอนนี้)_
- **Given** วิชา X ยังไม่มีผู้แนะนำคนใดผ่านการอนุมัติเลย — **When** นักศึกษาทั่วไปเปิดห้องแชทของวิชา X — **Then** ห้องแชทต้องแสดงสถานะว่ายังไม่มีผู้แนะนำ/ยังไม่มีข้อความ โดยไม่เกิด error _(ต้องการข้อมูลเพิ่มเติมจากผู้ใช้ — ไม่มี fallback ระบุใน spec, อ้างอิง Edge Case journey นักศึกษาทั่วไป)_

### AC-6: ผู้ดูแลระบบตรวจสอบเนื้อหาก่อนเผยแพร่ (pre-moderation queue)
**อ้างอิง User Story:** "ในฐานะผู้ดูแลระบบ ฉันต้องการตรวจสอบเนื้อหาที่ถูกโพสต์ในห้องแชทก่อนเผยแพร่ เพื่อให้มั่นใจว่าคำแนะนำที่ปรากฏเหมาะสมและเป็นประโยชน์" (US5, อ้าง Business Rule pre-moderation)

- **Given** มีข้อความใหม่ถูกส่งเข้าห้องแชทของวิชาใดวิชาหนึ่ง (จากผู้แนะนำหรือนักศึกษาทั่วไป)
- **When** ข้อความถูกส่ง
- **Then** ข้อความต้องปรากฏในคิวตรวจสอบก่อนเผยแพร่ของผู้ที่รับผิดชอบ pre-moderation _(ต้องการข้อมูลเพิ่มเติมจากผู้ใช้: ผู้รับผิดชอบคือแอดมินส่วนกลางหรืออาจารย์ประจำวิชา — สมมติฐานที่ใช้ในการร่างนี้คือ "ผู้ดูแลระบบ" ตามคำที่ spec ระบุไว้เป็นค่าเริ่มต้น)_
- **Given** ข้อความอยู่ในคิวตรวจสอบ — **When** ผู้ดูแลระบบ approve ข้อความ — **Then** ข้อความต้องเผยแพร่ให้นักศึกษาที่มีสิทธิ์ในห้องแชทวิชานั้นเห็นทันที
- **Given** ข้อความอยู่ในคิวตรวจสอบ — **When** ผู้ดูแลระบบ reject ข้อความ — **Then** ข้อความต้องไม่ถูกเผยแพร่ และไม่มีนักศึกษาคนอื่นเห็นเนื้อหานั้น
- **Given** มีข้อความ/รายชื่อจำนวนมากรอในคิวพร้อมกันหลายวิชา — ระยะเวลาที่ยอมรับได้ในการตรวจสอบ (SLA) _(ต้องการข้อมูลเพิ่มเติมจากผู้ใช้ — spec ระบุตรงๆ ว่ายังไม่กำหนด SLA)_
