# Test Plan: ระบบเตือนและแนะนำแนวทางการเรียนส่วนบุคคล

**สร้างจาก:** [[../../01-requirements/01-spec/20260825-01-personalized-learning-reminder|ระบบเตือนและแนะนำแนวทางการเรียนส่วนบุคคล]]
**อ้างอิง Acceptance Criteria:** [[./20260904-01-acceptance-criteria-personalized-learning-reminder|Acceptance Criteria]]
**วันที่สร้าง:** 2026-09-04

## ขอบเขตการทดสอบ (Scope)

### อยู่ในขอบเขต (In Scope)
- การติดตามตัวแปรผลการเรียนของนักเรียน/นักศึกษา (เกรด, การเข้าเรียน, การส่งงาน, แนวโน้ม)
- การประเมินเงื่อนไขความเสี่ยงจากหลายตัวแปรร่วมกัน โดยเกณฑ์ตั้งค่าได้ (configurable)
- การแจ้งเตือนแบบ in-app ทันทีที่ตรวจพบเงื่อนไขความเสี่ยง
- การแสดงสรุปภาพรวมสถานการณ์การเรียนรายสัปดาห์
- การให้คำแนะนำแนวทางการเรียนเฉพาะบุคคลจากข้อมูลย้อนหลัง
- หน้าจัดการเกณฑ์/ตัวแปรสำหรับผู้ดูแลระบบ

### ไม่อยู่ในขอบเขต (Out of Scope)
- การใช้งานจริงในบริบทองค์กร/บริษัท (เป็นเพียงแนวทางออกแบบเผื่ออนาคต)
- ช่องทางแจ้งเตือนอื่นนอกเหนือ in-app เช่น อีเมล, LINE, SMS
- การเชื่อมต่อกับระบบเกรด/ระบบภายนอกที่ยังไม่ได้ระบุแหล่งข้อมูลชัดเจน

## Test Strategy

เนื่องจาก feature ในเวอร์ชันนี้ประกอบด้วย (1) background process ประเมินเงื่อนไขหลายตัวแปร (2) การคำนวณคำแนะนำเฉพาะบุคคล และ (3) UI สำหรับผู้เรียน/ผู้ดูแลระบบ แนะนำให้ทดสอบเป็น 3 ระดับ:

- **Unit-level:** ทดสอบตรรกะการประเมินเงื่อนไขแต่ละตัวแปร (grade/attendance/assignment/trend) แยกจากกัน และตรรกะการคำนวณคำแนะนำเฉพาะบุคคล — เหมาะกับ automated test
- **Integration-level:** ทดสอบว่าการเปลี่ยนค่าเกณฑ์จากหน้าจัดการของผู้ดูแลระบบมีผลต่อผลลัพธ์การประเมินความเสี่ยงจริง และการแจ้งเตือนถูกสร้าง/ส่งเมื่อเข้าเงื่อนไข — ผสม automated + manual
- **E2E/Manual:** ทดสอบ flow ของผู้เรียนตาม user journey ตั้งแต่เข้าเงื่อนไขเสี่ยง → ได้รับแจ้งเตือน → เห็นคำแนะนำ → เปิดดูสรุปรายสัปดาห์ — แนะนำ manual test ในเวอร์ชันนี้เนื่องจากยังไม่มี UI/technical design ที่ชัดเจนพอสำหรับ automation

## Test Data
- บัญชีผู้เรียนที่มีข้อมูลย้อนหลังครบ (เกรด, การเข้าเรียน, การส่งงาน, แนวโน้มหลายช่วงเวลา) สำหรับทดสอบ happy path และคำแนะนำเฉพาะบุคคล
- บัญชีผู้เรียนใหม่ที่ยังไม่มีข้อมูลย้อนหลัง (หรือมีน้อยกว่าเกณฑ์ที่ระบบต้องใช้คำนวณ) สำหรับทดสอบ edge case fallback
- บัญชีผู้เรียนอย่างน้อย 2 คนที่มีสถานการณ์ต่างกัน (เช่น คนหนึ่งเกรดต่ำ อีกคนขาดเรียนบ่อย) เพื่อเปรียบเทียบว่าคำแนะนำที่ได้ไม่เหมือนกัน
- บัญชีผู้เรียนที่เข้าเงื่อนไขเสี่ยงหลายตัวแปรพร้อมกันในรอบประเมินเดียว
- บัญชีผู้ดูแลระบบสำหรับเข้าหน้าจัดการเกณฑ์/ตัวแปร
- ค่าตัวเลขเกณฑ์จริงสำหรับทดสอบ boundary (เช่น เกรดขั้นต่ำ, จำนวนวันขาดเรียน, จำนวนงานที่ไม่ส่ง, จำนวนช่วงเวลาที่แนวโน้มลดลงต่อเนื่อง) _(ต้องการข้อมูลเพิ่มเติมจากผู้ใช้ — spec ยังไม่ระบุค่าจริง ให้ผู้ดำเนินการทดสอบกำหนดค่าเกณฑ์ทดสอบเองในสภาพแวดล้อม staging ก่อนรัน test case ที่เกี่ยวกับ boundary)_

หมายเหตุ Priority: อ้างอิงจาก MoSCoW ในเอกสาร Features List — ฟีเจอร์ #1-4, #6 เป็น Must have จึงให้ Priority High กับ TC ที่ทดสอบ happy path หลักของฟีเจอร์เหล่านั้น (TC-01, TC-04, TC-05, TC-09), ฟีเจอร์ #5 (สรุปรายสัปดาห์) เป็น Should have จึงให้ Priority Medium/Low ตามลำดับความสำคัญของ TC, ส่วน edge case ที่ spec ยังไม่ระบุพฤติกรรมชัดเจน (TC-03, TC-06, TC-11) ให้ Priority Medium/Low ไว้ก่อนเนื่องจากยังไม่สามารถยืนยัน severity ได้จนกว่าจะมีข้อมูลเพิ่มเติม
