# Test Plan: ระบบเตือนและแนะนำแนวทางการเรียนส่วนบุคคล

**สร้างจาก:** [[../../01-requirements/01-spec/20260825-01-personalized-learning-reminder|ระบบเตือนและแนะนำแนวทางการเรียนส่วนบุคคล]]
**อ้างอิง Acceptance Criteria:** [[./20260907-01-acceptance-criteria-personalized-learning-reminder|Acceptance Criteria]]
**วันที่สร้าง:** 2026-09-07

## ขอบเขตการทดสอบ (Scope)

### อยู่ในขอบเขต (In Scope)
- การติดตามตัวแปรผลการเรียนของนักเรียน/นักศึกษา (เกรด, การเข้าเรียน, การส่งงาน, แนวโน้ม) — ฟีเจอร์ #1
- การประเมินเงื่อนไขความเสี่ยงจากหลายตัวแปรร่วมกันแบบ configurable — ฟีเจอร์ #2
- การแจ้งเตือนแบบ in-app ทันทีที่ตรวจพบเงื่อนไข — ฟีเจอร์ #3
- คำแนะนำแนวทางการเรียนเฉพาะบุคคลจากข้อมูลย้อนหลัง — ฟีเจอร์ #4
- สรุปภาพรวมสถานการณ์การเรียนรายสัปดาห์ — ฟีเจอร์ #5
- หน้าจัดการเกณฑ์/ตัวแปรสำหรับผู้ดูแลระบบ — ฟีเจอร์ #6
- การตรวจสอบเชิงออกแบบว่าโครงสร้างรองรับหมวดหมู่ผู้ใช้งานอื่นในอนาคต (ไม่ทดสอบการใช้งานจริงนอกบริบทการเรียน) — ฟีเจอร์ #7

### ไม่อยู่ในขอบเขต (Out of Scope)
- การนำระบบไปใช้งานจริงในบริบทองค์กร/บริษัท (ฟีเจอร์ #9)
- ช่องทางแจ้งเตือนอื่นนอกเหนือจาก in-app เช่น อีเมล, LINE, SMS (ฟีเจอร์ #8)
- การเชื่อมต่อกับระบบเกรด/ระบบภายนอกอื่นที่ยังไม่ได้ระบุแหล่งข้อมูลชัดเจน (ฟีเจอร์ #10)

## Test Strategy

- **การประเมินเงื่อนไขความเสี่ยงหลายตัวแปร (ฟีเจอร์ #1, #2)** และ **เอนจินคำนวณคำแนะนำเฉพาะบุคคล (ฟีเจอร์ #4)** เป็น business logic หลักของระบบ ควรทดสอบด้วย automated unit/integration test เป็นหลัก โดยเฉพาะการทดสอบค่าขอบเขต (boundary) ของแต่ละเกณฑ์ (เช่น GPA = 2.00 พอดี, อัตราขาดเรียน = 80% พอดี) เนื่องจากค่าตัวเลขที่ใช้เป็นสมมติฐานที่มีความอ่อนไหวต่อความถูกต้อง
- **การแจ้งเตือน in-app (ฟีเจอร์ #3), หน้าสรุปรายสัปดาห์ (ฟีเจอร์ #5), หน้าจัดการเกณฑ์ของแอดมิน (ฟีเจอร์ #6)** เป็นส่วน UI/flow ที่ผู้ใช้สัมผัสโดยตรง ควรทดสอบแบบ manual/E2E ร่วมกับ integration test เพื่อยืนยันว่าผลจาก business logic แสดงผลถูกต้องบนหน้าจอ
- **สถาปัตยกรรมรองรับหมวดหมู่อื่นในอนาคต (ฟีเจอร์ #7)** ทดสอบด้วยวิธี architecture/config review (ตรวจสอบโครงสร้างข้อมูล/สคีมา) ไม่ใช่ functional test เนื่องจากยังไม่ implement การใช้งานจริง
- Edge case ทั้งหมด (นักเรียนใหม่ไม่มีข้อมูลพอ, เข้าเงื่อนไขหลายตัวแปรพร้อมกัน, แอดมินปรับเกณฑ์ระหว่างมีแจ้งเตือนค้าง) ควรมี integration test เฉพาะเจาะจง เนื่องจากเป็นจุดที่ spec ไม่ได้ระบุพฤติกรรมไว้ชัดเจนและมีความเสี่ยงสูงที่จะ implement ผิดจากที่คาดหวัง

## Test Data

- บัญชีผู้ใช้ persona นักเรียน/นักศึกษา อย่างน้อย 5 แบบ:
  1. Baseline — ไม่เข้าเงื่อนไขเสี่ยงใดๆ
  2. เสี่ยงจากเกรดต่ำกว่าเกณฑ์เพียงตัวแปรเดียว (GPA < 2.00)
  3. เสี่ยงจากอัตราขาดเรียนเพียงตัวแปรเดียว (< 80% attendance)
  4. เสี่ยงจากหลายตัวแปรพร้อมกัน (เกรดต่ำ + ขาดเรียนเกิน + ไม่ส่งงานเกิน)
  5. นักเรียนใหม่ที่มีข้อมูลย้อนหลังน้อยกว่า 2 ช่วงเวลาประเมิน
- บัญชีผู้ดูแลระบบ (admin) อย่างน้อย 1 บัญชี พร้อมสิทธิ์เข้าหน้าจัดการเกณฑ์
- ชุดค่าเกณฑ์ตั้งต้น _(สมมติฐาน)_: GPA < 2.00, อัตราขาดเรียน < 80%, ไม่ส่งงานสะสม ≥ 3 ครั้ง, แนวโน้มลดลงต่อเนื่อง ≥ 2 ช่วงเวลาประเมิน
- ชุดค่าเกณฑ์ที่ผิดปกติสำหรับทดสอบ negative case ของหน้าจัดการเกณฑ์ (ค่าติดลบ, ค่าไม่ใช่ตัวเลข, ค่าว่าง)
- ข้อมูลการแจ้งเตือนที่ยังไม่ได้อ่าน (unread) ค้างอยู่ในระบบ สำหรับทดสอบ edge case การเปลี่ยนเกณฑ์ของแอดมิน
