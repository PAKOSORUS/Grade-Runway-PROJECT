## TS-12: แอดมินแก้ไขค่าเกณฑ์สำเร็จและมีผลทันทีในรอบประเมินถัดไป

**อ้างอิงจาก:** TC-12 / AC-4 (main flow) / BR2 — "เกณฑ์ต้อง configurable ห้าม hardcode"
**Priority:** High
**ประเภท:** Positive

### วัตถุประสงค์
ยืนยันว่าแอดมินแก้ไขค่าเกณฑ์ผ่านหน้าจัดการเกณฑ์ได้จริง และค่าใหม่มีผลต่อการประเมินเงื่อนไขความเสี่ยงในรอบถัดไปทันทีโดยไม่ต้องแก้โค้ด

### Precondition
- มีบัญชีแอดมินที่มีสิทธิ์เข้าหน้าจัดการเกณฑ์
- ค่าเกณฑ์อัตราขาดเรียนปัจจุบันตั้งไว้ที่ 80%
- มีบัญชีผู้ใช้ทดสอบที่มีอัตราเข้าเรียน 76% (ต่ำกว่า 80% แต่จะสูงกว่าเกณฑ์ใหม่ 75%)

### Test Data / Environment
| รายการ | ค่าก่อนทดสอบ | ค่าหลังทดสอบ |
|---|---|---|
| ค่าเกณฑ์อัตราขาดเรียน | 80% | 75% |
| อัตราเข้าเรียนของผู้ใช้ทดสอบ | 76% (ไม่เปลี่ยน) | 76% (ไม่เปลี่ยน) |

### ขั้นตอนทดสอบ

| # | การกระทำ | Input | ผลลัพธ์ที่คาดหวัง |
|---|---|---|---|
| 1 | Login เป็นแอดมินแล้วเปิดหน้าจัดการเกณฑ์/ตัวแปร | บัญชีแอดมิน | หน้าจัดการเกณฑ์แสดงค่าปัจจุบัน (80%) |
| 2 | ยืนยันว่าผู้ใช้ทดสอบ (attendance 76%) ถูกจัดเป็นเสี่ยงตามเกณฑ์เดิม | สั่งประเมินเงื่อนไขก่อนเปลี่ยนเกณฑ์ | ผู้ใช้ทดสอบถูกจัดเป็นเสี่ยง (76% < 80%) |
| 3 | แก้ไขค่าเกณฑ์อัตราขาดเรียนจาก 80% เป็น 75% แล้วกดบันทึก | ค่าเกณฑ์ใหม่ = 75% | ระบบบันทึกค่าเกณฑ์ใหม่สำเร็จ แสดงข้อความยืนยัน |
| 4 | สั่งให้ระบบประเมินเงื่อนไขความเสี่ยงรอบใหม่สำหรับผู้ใช้ทดสอบ (attendance ยังคง 76%) | — | ระบบประมวลผลสำเร็จ |
| 5 | ตรวจสอบสถานะความเสี่ยงของผู้ใช้ทดสอบหลังเปลี่ยนเกณฑ์ | — | ผู้ใช้ทดสอบ **ไม่ถูกจัดเป็นเสี่ยง** อีกต่อไป (76% > 75% เกณฑ์ใหม่) โดยไม่ต้องแก้โค้ด |

### ผลลัพธ์รวมที่คาดหวัง (Expected Result)
ค่าเกณฑ์ใหม่ที่แอดมินบันทึกมีผลต่อการประเมินเงื่อนไขความเสี่ยงในรอบถัดไปทันที สอดคล้องกับ BR2

### Postcondition
คืนค่าเกณฑ์อัตราขาดเรียนกลับเป็น 80% (ค่าตั้งต้น) ก่อนใช้ในเทสเคสอื่น เพื่อไม่ให้กระทบผลของ TS-02, TS-06

### Dependency
ควรรันหลัง TS-02 (ยืนยันว่า engine ตรวจจับเงื่อนไขอัตราเข้าเรียนทำงานถูกต้องด้วยเกณฑ์เดิมก่อน)

## TS-13: ระบบปฏิเสธการบันทึกค่าเกณฑ์ที่ไม่ถูกต้อง

**อ้างอิงจาก:** TC-13 / AC-4 (negative)
**Priority:** High
**ประเภท:** Negative

### วัตถุประสงค์
ยืนยันว่าระบบตรวจสอบความถูกต้องของค่าเกณฑ์ก่อนบันทึก และปฏิเสธค่าที่ไม่สมเหตุสมผล (ค่าติดลบ, ไม่ใช่ตัวเลข) โดยไม่กระทบค่าเกณฑ์เดิม

### Precondition
- มีบัญชีแอดมินที่มีสิทธิ์เข้าหน้าจัดการเกณฑ์
- ค่าเกณฑ์ปัจจุบันของตัวแปรที่จะทดสอบมีค่าที่ใช้งานได้ปกติอยู่แล้ว (เช่น อัตราขาดเรียน = 80%)

### Test Data / Environment
| กรณีย่อย | ค่าที่กรอก |
|---|---|
| 13a | -5 (ค่าติดลบ) |
| 13b | "abc" (ไม่ใช่ตัวเลข) |
| 13c | ค่าว่าง (ไม่กรอกอะไรเลย) |

### ขั้นตอนทดสอบ

| # | การกระทำ | Input | ผลลัพธ์ที่คาดหวัง |
|---|---|---|---|
| 1 | Login เป็นแอดมินแล้วเปิดหน้าจัดการเกณฑ์ | บัญชีแอดมิน | หน้าจัดการเกณฑ์แสดงค่าปัจจุบันถูกต้อง |
| 2 | กรอกค่าเกณฑ์เป็น -5 (กรณี 13a) แล้วกดบันทึก | -5 | ระบบปฏิเสธการบันทึก แสดงข้อความแจ้งข้อผิดพลาด (เช่น "ค่าต้องไม่ติดลบ") ค่าเกณฑ์เดิมไม่เปลี่ยน |
| 3 | กรอกค่าเกณฑ์เป็น "abc" (กรณี 13b) แล้วกดบันทึก | "abc" | ระบบปฏิเสธการบันทึก แสดงข้อความแจ้งข้อผิดพลาด (เช่น "ต้องเป็นตัวเลข") ค่าเกณฑ์เดิมไม่เปลี่ยน |
| 4 | ลบค่าในช่องกรอกให้ว่างเปล่า (กรณี 13c) แล้วกดบันทึก | ค่าว่าง | ระบบปฏิเสธการบันทึก แสดงข้อความแจ้งว่าต้องกรอกค่า ค่าเกณฑ์เดิมไม่เปลี่ยน |
| 5 | รีเฟรชหน้าจัดการเกณฑ์อีกครั้งหลังพยายามบันทึกทั้ง 3 กรณี | — | ค่าเกณฑ์ที่แสดงยังคงเป็นค่าเดิมก่อนการพยายามบันทึกที่ผิดพลาด (ไม่มีค่าใดหลุดรอดเข้าไปบันทึกจริง) |

### ผลลัพธ์รวมที่คาดหวัง (Expected Result)
ระบบต้อง validate ค่าเกณฑ์ก่อนบันทึกทุกครั้ง ปฏิเสธค่าที่ไม่ถูกต้องทั้ง 3 รูปแบบ และไม่กระทบค่าเกณฑ์เดิมที่ใช้งานอยู่

### Postcondition
ไม่ต้อง reset ข้อมูล (การบันทึกถูกปฏิเสธทั้งหมด ค่าเดิมไม่เปลี่ยน)

### Dependency
ไม่พึ่งพาเทสเคสอื่น

## TS-14: การแจ้งเตือนที่ค้างอยู่ไม่เปลี่ยนแปลงเมื่อแอดมินปรับเกณฑ์ใหม่

**อ้างอิงจาก:** TC-14 / AC-4 (edge case) — สอดคล้องกับ Edge Cases ของ User Journey ("ผู้ดูแลระบบปรับเปลี่ยนเกณฑ์ระหว่างที่มีการแจ้งเตือนที่ยังไม่ได้อ่านค้างอยู่")
**Priority:** Medium
**ประเภท:** Edge

### วัตถุประสงค์
ยืนยันว่าการแจ้งเตือนที่สร้างไว้ก่อนหน้าตามเกณฑ์เดิม (snapshot) ไม่ถูกเปลี่ยนแปลงเนื้อหาย้อนหลังเมื่อแอดมินปรับเกณฑ์ใหม่ในภายหลัง

### Precondition
- มีการแจ้งเตือนที่ยังไม่ได้อ่านค้างอยู่ในระบบ ซึ่งสร้างจาก TS-01 (เงื่อนไข "เกรดต่ำกว่าเกณฑ์" ที่เกณฑ์ GPA < 2.00)
- มีบัญชีแอดมินที่มีสิทธิ์เข้าหน้าจัดการเกณฑ์

### Test Data / Environment
| รายการ | ค่า |
|---|---|
| การแจ้งเตือนค้าง (unread) | จาก TS-01 — เงื่อนไข "เกรดต่ำกว่าเกณฑ์" ที่ GPA < 2.00 |
| ค่าเกณฑ์ GPA ใหม่ที่แอดมินจะตั้ง | < 1.80 (เข้มงวดน้อยลง) |

### ขั้นตอนทดสอบ

| # | การกระทำ | Input | ผลลัพธ์ที่คาดหวัง |
|---|---|---|---|
| 1 | ตรวจสอบและบันทึกเนื้อหาการแจ้งเตือนค้าง (จาก TS-01) ก่อนเปลี่ยนเกณฑ์ | การแจ้งเตือนค้างจาก TS-01 | ได้เนื้อหาต้นฉบับ: เงื่อนไข "เกรดต่ำกว่าเกณฑ์" อ้างอิงเกณฑ์ GPA < 2.00 |
| 2 | Login เป็นแอดมิน เปิดหน้าจัดการเกณฑ์ แก้ค่าเกณฑ์ GPA จาก 2.00 เป็น 1.80 แล้วบันทึก | ค่าเกณฑ์ใหม่ = 1.80 | บันทึกสำเร็จ |
| 3 | เปิดดูการแจ้งเตือนที่ค้างอยู่ก่อนหน้า (จากสเต็ป 1) อีกครั้ง | — | เนื้อหาการแจ้งเตือนยังคงเดิม อ้างอิงเกณฑ์ ณ ตอนตรวจพบ (GPA < 2.00) ไม่เปลี่ยนเป็นเกณฑ์ใหม่ (1.80) |
| 4 | สั่งให้ระบบประเมินเงื่อนไขความเสี่ยงรอบใหม่สำหรับผู้ใช้เดิม (GPA ไม่เปลี่ยน) | — | ระบบใช้เกณฑ์ใหม่ (1.80) ในการประเมินรอบถัดไปเท่านั้น ไม่ย้อนแก้ผลที่เกิดไปแล้ว |

### ผลลัพธ์รวมที่คาดหวัง (Expected Result)
การแจ้งเตือนที่ค้างอยู่คงเนื้อหาเดิมตามเกณฑ์ ณ ตอนตรวจพบ (snapshot) เกณฑ์ใหม่มีผลเฉพาะการประเมินรอบถัดไปเท่านั้น

### หมายเหตุ (สมมติฐาน)
พฤติกรรม "snapshot" นี้เป็นการอนุมานจาก AC-4 เนื่องจาก spec ต้นทางไม่ได้ระบุผลกระทบต่อการแจ้งเตือนค้างไว้ชัดเจน ควรยืนยันกับผู้ใช้/นักออกแบบอีกครั้งหากพฤติกรรมจริงต่างจากนี้

### Postcondition
คืนค่าเกณฑ์ GPA กลับเป็น 2.00 (ค่าตั้งต้น) ก่อนใช้ในเทสเคสอื่น

### Dependency
ต้องรันหลัง TS-01 (ต้องมีการแจ้งเตือนค้างอยู่ก่อน)

## TS-15: โครงสร้างข้อมูลรองรับหมวดหมู่ผู้ใช้งานอื่นในอนาคต (เชิงออกแบบ)

**อ้างอิงจาก:** TC-15 / AC-5 — ฟีเจอร์ #7 (Could have, ยังไม่ implement การใช้งานจริงนอกบริบทการเรียน)
**Priority:** Low
**ประเภท:** Positive (Design/Architecture Review — ไม่ใช่ functional test)

### วัตถุประสงค์
ยืนยันว่าฟิลด์ "หมวดหมู่ผู้ใช้งาน" ในโครงสร้างข้อมูล/สคีมาถูกออกแบบเป็นค่า configurable ไม่ hardcode เฉพาะ "นักเรียน/นักศึกษา" เพื่อให้รองรับการขยายไปหมวดหมู่อื่น (เช่น องค์กร) ได้ในอนาคตโดยไม่ต้องแก้โครงสร้างหลัก

### Precondition
- มีเอกสารออกแบบสคีมา/โมเดลข้อมูลของระบบเงื่อนไข-เกณฑ์ที่ [[../../02-design/02-technical/index|02-technical]] (หรือสคีมาฐานข้อมูลจริงถ้ามีการ implement แล้ว)

### Test Data / Environment
| รายการ | ที่มา |
|---|---|
| เอกสาร/สคีมาที่ตรวจสอบ | เอกสารออกแบบฐานข้อมูล/โมเดลข้อมูลของระบบเงื่อนไข-เกณฑ์ |

### ขั้นตอนทดสอบ

| # | การกระทำ | Input | ผลลัพธ์ที่คาดหวัง |
|---|---|---|---|
| 1 | เปิดเอกสารออกแบบสคีมา/โมเดลข้อมูลของ "หมวดหมู่ผู้ใช้งาน" | เอกสารออกแบบ/สคีมา | พบฟิลด์ที่ใช้แทนหมวดหมู่ผู้ใช้งาน |
| 2 | ตรวจสอบว่าฟิลด์นั้นเป็นค่าที่กำหนดได้ (เช่น enum/reference table ที่เพิ่มค่าใหม่ได้) หรือถูก hardcode ไว้เฉพาะ "นักเรียน/นักศึกษา" | — | ฟิลด์ต้องเป็นค่า configurable (เช่น lookup table หรือ enum ที่ขยายได้) ไม่ hardcode ในโค้ด |
| 3 | ตรวจสอบว่าเงื่อนไข/เกณฑ์ความเสี่ยง (จาก AC-4) ผูกกับหมวดหมู่ผู้ใช้งานแบบ reference ไม่ใช่ผูกตายตัวกับ "นักเรียน/นักศึกษา" | — | เงื่อนไข/เกณฑ์อ้างอิงหมวดหมู่ผ่าน field/relation ที่เปลี่ยนได้ ไม่ผูกตายตัวในโค้ด |

### ผลลัพธ์รวมที่คาดหวัง (Expected Result)
โครงสร้างข้อมูลออกแบบให้ "หมวดหมู่ผู้ใช้งาน" เป็นค่า configurable ตาม Overview/Scope ของ spec แม้จะยังไม่มีการใช้งานจริงนอกบริบทการเรียนในเวอร์ชันนี้

### หมายเหตุ
นี่คือการตรวจสอบเชิงออกแบบ (design/architecture review) ไม่ใช่ functional test เต็มรูปแบบ เพราะฟีเจอร์นี้เป็น Could-have ที่ยังไม่ implement การใช้งานจริงนอกบริบทการเรียน — เหมาะกับการรีวิวเอกสาร/สคีมามากกว่าการทดสอบผ่าน UI

### Postcondition
ไม่มี (เป็นการรีวิวเอกสาร ไม่มีการเปลี่ยนแปลงข้อมูล)

### Dependency
ไม่พึ่งพาเทสเคสอื่น ควรทำหลังขั้นตอนออกแบบทางเทคนิค ([[../../02-design/02-technical/index|02-technical]]) เสร็จสมบูรณ์แล้ว
