# Acceptance Criteria: ระบบเตือนและแนะนำแนวทางการเรียนส่วนบุคคล

**สร้างจาก:** [[../../01-requirements/01-spec/20260825-01-personalized-learning-reminder|ระบบเตือนและแนะนำแนวทางการเรียนส่วนบุคคล]]
**เกี่ยวข้องกับ:** [[../../02-design/01-prototypes/20260827-01-features-list-personalized-learning-reminder|Features List]], [[../../02-design/01-prototypes/20260827-02-user-journey-student-personalized-learning-reminder|User Journey: นักเรียน/นักศึกษา]]
**วันที่สร้าง:** 2026-09-07

## Acceptance Criteria ต่อ User Story

### AC-1: แจ้งเตือนเมื่อเข้าเงื่อนไขเสี่ยงจากหลายตัวแปร
**อ้างอิง User Story (US1):** "ในฐานะนักเรียน/นักศึกษา ฉันต้องการได้รับการแจ้งเตือนเมื่อผลการเรียนหรือพฤติกรรมการเรียนของฉันเข้าเงื่อนไขที่มีความเสี่ยง เพื่อที่จะปรับตัวได้ทันเวลาก่อนปัญหาลุกลาม" (ฟีเจอร์ #1, #2, #3)

- **Given** นักเรียน/นักศึกษามีเกรดเฉลี่ยสะสม (GPA) ต่ำกว่า 2.00 _(สมมติฐาน: เกณฑ์ตั้งต้น)_
- **When** ระบบประเมินตัวแปรผลการเรียนของผู้ใช้รอบล่าสุด
- **Then** ระบบต้องส่งการแจ้งเตือนแบบ in-app ทันที ระบุว่าเงื่อนไข "เกรดต่ำกว่าเกณฑ์" ถูกกระตุ้น (BR: เงื่อนไขแจ้งเตือน + ช่องทาง in-app ทันที)

- **Given** อัตราการเข้าเรียนของผู้ใช้ต่ำกว่า 80% ของชั่วโมงเรียนทั้งหมดในรายวิชา _(สมมติฐาน)_
- **When** ระบบประเมินข้อมูลการเข้าเรียนรอบล่าสุด
- **Then** ระบบต้องส่งการแจ้งเตือนแบบ in-app ทันที ระบุว่าเงื่อนไข "อัตราขาดเรียนเกินเกณฑ์" ถูกกระตุ้น

- **Given** ผู้ใช้ไม่ส่งงาน/ไม่ทำแบบทดสอบสะสมตั้งแต่ 3 ครั้งขึ้นไปในรายวิชาเดียวกัน _(สมมติฐาน)_
- **When** ระบบประเมินข้อมูลการส่งงานรอบล่าสุด
- **Then** ระบบต้องส่งการแจ้งเตือนแบบ in-app ทันที ระบุว่าเงื่อนไข "ไม่ส่งงานเกินเกณฑ์" ถูกกระตุ้น

- **Given** คะแนนสอบ/คะแนนเก็บของผู้ใช้ลดลงติดต่อกันอย่างน้อย 2 ช่วงเวลาประเมิน _(สมมติฐาน)_
- **When** ระบบประเมินแนวโน้มผลการเรียน
- **Then** ระบบต้องส่งการแจ้งเตือนแบบ in-app ทันที ระบุว่าเงื่อนไข "แนวโน้มผลการเรียนลดลงต่อเนื่อง" ถูกกระตุ้น

- **Given** ผู้ใช้ไม่เข้าเงื่อนไขเสี่ยงข้อใดเลย
- **When** ระบบประเมินข้อมูลรอบล่าสุด
- **Then** ระบบต้องไม่ส่งการแจ้งเตือนความเสี่ยง

- **Edge case (ผู้ใช้เข้าเงื่อนไขเสี่ยงหลายตัวแปรพร้อมกัน):**
  - **Given** ผู้ใช้เข้าเงื่อนไขเสี่ยงมากกว่า 1 ตัวแปรพร้อมกันในรอบประเมินเดียว
  - **When** ระบบตรวจพบเงื่อนไขทั้งหมด
  - **Then** ระบบต้องส่งการแจ้งเตือนแบบรวม (consolidated) หนึ่งรายการที่ระบุทุกเงื่อนไขที่ถูกกระตุ้น แทนการส่งแยกหลายรายการ _(สมมติฐาน: spec ไม่ได้ระบุลำดับความสำคัญ/การจัดกลุ่มไว้)_

- **Edge case (เปิดดูรายละเอียดการแจ้งเตือน — คะแนนความมั่นใจต่ำในJourney):**
  - **Given** ผู้ใช้ได้รับการแจ้งเตือนความเสี่ยงแล้ว
  - **When** ผู้ใช้เปิดดูรายละเอียดการแจ้งเตือน
  - **Then** หน้ารายละเอียดต้องแสดงเงื่อนไขที่ถูกกระตุ้นทั้งหมด และมีลิงก์นำไปสู่หน้าคำแนะนำเฉพาะบุคคลที่เกี่ยวข้อง _(สมมติฐาน: spec ไม่ได้ระบุรูปแบบเนื้อหา/UI ของการแจ้งเตือน)_

### AC-2: คำแนะนำแนวทางการเรียนเฉพาะบุคคล
**อ้างอิง User Story (US2):** "ในฐานะนักเรียน/นักศึกษา ฉันต้องการเห็นคำแนะนำแนวทางการเรียนที่คำนวณเฉพาะสำหรับฉันจากข้อมูลผลการเรียนย้อนหลัง เพื่อให้คำแนะนำตรงกับสถานการณ์จริงของฉัน ไม่ใช่คำแนะนำสำเร็จรูปเดียวกันสำหรับทุกคน" (ฟีเจอร์ #4, #1)

- **Given** ผู้ใช้สองคนมีข้อมูลผลการเรียน/พฤติกรรมย้อนหลังที่แตกต่างกัน (เช่น คนหนึ่งเสี่ยงจากขาดเรียน อีกคนเสี่ยงจากไม่ส่งงาน)
- **When** ระบบคำนวณคำแนะนำแนวทางการเรียนให้ทั้งสองคน
- **Then** เนื้อหาคำแนะนำที่แสดงต่อผู้ใช้แต่ละคนต้องแตกต่างกันและสอดคล้องกับตัวแปรเสี่ยงเฉพาะของแต่ละคน (BR3: คำแนะนำเฉพาะบุคคล ห้ามเป็นข้อความสำเร็จรูปเดียวกัน)

- **Edge case (นักเรียนใหม่ยังไม่มีข้อมูลย้อนหลังพอ):**
  - **Given** ผู้ใช้มีข้อมูลผลการเรียนน้อยกว่า 2 ช่วงเวลาประเมิน _(สมมติฐาน: เกณฑ์ข้อมูลขั้นต่ำ)_
  - **When** ระบบพยายามคำนวณคำแนะนำเฉพาะบุคคล
  - **Then** ระบบต้องแสดงข้อความ fallback (เช่น "ยังไม่มีข้อมูลเพียงพอสำหรับคำแนะนำเฉพาะบุคคล") แทนการแสดงคำแนะนำที่คำนวณจากข้อมูลไม่เพียงพอ

### AC-3: สรุปภาพรวมสถานการณ์การเรียนรายสัปดาห์
**อ้างอิง User Story (US3):** "ในฐานะนักเรียน/นักศึกษา ฉันต้องการเห็นสรุปภาพรวมสถานการณ์การเรียนของตัวเองแบบรายสัปดาห์ นอกเหนือจากการแจ้งเตือนแบบทันที" (ฟีเจอร์ #5)

- **Given** ผู้ใช้มีข้อมูลผลการเรียนสะสมของสัปดาห์ที่ผ่านมา
- **When** ผู้ใช้เปิดหน้าสรุปภาพรวมรายสัปดาห์
- **Then** ระบบต้องแสดงสรุปสถานการณ์การเรียน (เกรด/การเข้าเรียน/การส่งงาน/แนวโน้ม) ของสัปดาห์นั้นๆ อย่างครบถ้วน (BR4: สรุปภาพรวมรายสัปดาห์นอกเหนือจากการแจ้งเตือนทันที)

- **Edge case (ประเมินความคืบหน้าเทียบสัปดาห์ก่อน — คะแนนความมั่นใจต่ำใน Journey):**
  - **Given** ผู้ใช้มีข้อมูลสรุปของสัปดาห์ปัจจุบันและสัปดาห์ก่อนหน้า
  - **When** ผู้ใช้ดูหน้าสรุปรายสัปดาห์
  - **Then** หน้าสรุปต้องแสดงการเปรียบเทียบ/แนวโน้ม (trend) กับสัปดาห์ก่อนหน้าอย่างน้อย 1 ตัวแปร _(สมมติฐาน: spec ไม่ได้ระบุรายละเอียดเนื้อหาการเปรียบเทียบ)_

---

### AC-4: ผู้ดูแลระบบปรับแต่งเกณฑ์/ตัวแปรการแจ้งเตือน
**อ้างอิง User Story (US4):** "ในฐานะผู้ดูแลระบบ ฉันต้องการปรับแต่งเกณฑ์/ตัวแปรที่ใช้ในการแจ้งเตือนได้ เพื่อให้ระบบยืดหยุ่นพอจะนำไปปรับใช้กับบริบทอื่นได้ในอนาคต" (ฟีเจอร์ #6, #2)

- **Given** ผู้ดูแลระบบเข้าสู่หน้าจัดการเกณฑ์/ตัวแปร
- **When** ผู้ดูแลระบบแก้ไขค่าเกณฑ์ (เช่น เปลี่ยนเกณฑ์อัตราขาดเรียนจาก 80% เป็น 75%) แล้วบันทึก
- **Then** ระบบต้องบันทึกค่าใหม่และนำไปใช้ในการประเมินเงื่อนไขความเสี่ยงรอบถัดไปทันที โดยไม่ต้องแก้โค้ด (BR2: เกณฑ์ต้อง configurable ห้าม hardcode)

- **Given** ผู้ดูแลระบบกรอกค่าเกณฑ์ที่ไม่ถูกต้อง (เช่น ค่าติดลบ หรือไม่ใช่ตัวเลข)
- **When** ผู้ดูแลระบบพยายามบันทึก
- **Then** ระบบต้องปฏิเสธการบันทึกและแสดงข้อความแจ้งข้อผิดพลาด

- **Edge case (แอดมินปรับเกณฑ์ระหว่างมีการแจ้งเตือนค้างอยู่):**
  - **Given** มีการแจ้งเตือนที่ยังไม่ได้อ่านค้างอยู่ในระบบซึ่งถูกสร้างจากเกณฑ์เดิม
  - **When** ผู้ดูแลระบบเปลี่ยนค่าเกณฑ์ใหม่
  - **Then** เนื้อหาการแจ้งเตือนที่ค้างอยู่ต้องคงเดิมตามเกณฑ์ ณ ตอนที่ตรวจพบ (snapshot) เกณฑ์ใหม่มีผลเฉพาะการประเมินรอบถัดไปเท่านั้น _(สมมติฐาน: spec ไม่ได้ระบุผลกระทบต่อการแจ้งเตือนค้าง)_

### AC-5: สถาปัตยกรรมรองรับหมวดหมู่ผู้ใช้งานอื่นในอนาคต (เชิงออกแบบ)
**อ้างอิง User Story:** Overview / Scope (In Scope ข้อ 4) — "ระบบต้องออกแบบให้เงื่อนไขการแจ้งเตือนและหมวดหมู่ผู้ใช้งานสามารถกำหนดค่าได้ (configurable)" (ฟีเจอร์ #7 — Could have, ยัง**ไม่ implement**การใช้งานจริงนอกบริบทการเรียน)

- **Given** โมเดลข้อมูลของระบบเงื่อนไข/เกณฑ์การแจ้งเตือน
- **When** ผู้พัฒนา/ผู้ดูแลระบบตรวจสอบโครงสร้างการตั้งค่า
- **Then** "หมวดหมู่ผู้ใช้งาน" ต้องถูกแทนด้วยฟิลด์/เอนทิตีที่ configurable ไม่ hardcode เฉพาะ "นักเรียน/นักศึกษา" เพื่อให้เพิ่มหมวดหมู่อื่นได้ในอนาคตโดยไม่ต้องแก้โครงสร้างหลัก (Overview: รองรับบริบทอื่นในอนาคต) — หมายเหตุ: เป็นการตรวจสอบเชิงออกแบบ ไม่ใช่การทดสอบ functional เต็มรูปแบบ เนื่องจากยังไม่ implement การใช้งานจริงนอกบริบทการเรียน
