# Acceptance Criteria: การเก็บ Log กิจกรรมและการปฏิบัติตาม PDPA

**สร้างจาก:** [[../../01-requirements/01-spec/20260825-03-logging-pdpa-compliance|การเก็บ Log กิจกรรมและการปฏิบัติตาม PDPA]]
**เกี่ยวข้องกับ:** [[../../02-design/01-prototypes/20261007-01-features-list-logging-pdpa-compliance|Features List]], [[../../02-design/01-prototypes/20261007-02-user-journey-auditor-logging-pdpa-compliance|User Journey: ผู้ตรวจสอบ]], [[../../02-design/01-prototypes/20261007-03-user-journey-data-subject-logging-pdpa-compliance|User Journey: เจ้าของข้อมูล]], [[../../02-design/01-prototypes/20261007-04-user-journey-data-controller-logging-pdpa-compliance|User Journey: เจ้าหน้าที่ PDPA]]
**วันที่สร้าง:** 2026-10-07

หมายเหตุ: US1-US5 เรียงตามลำดับ User Stories ใน spec (US1 = ผู้ดูแลระบบดู log ย้อนหลัง, US2 = เจ้าของข้อมูลรับรู้วัตถุประสงค์และให้/ถอน consent, US3 = เจ้าของข้อมูลร้องขอเข้าถึง/แก้ไข/ลบ, US4 = สถาบันรองรับคำร้องและแจ้งเหตุรั่วไหล, US5 = ผู้ดูแลระบบมั่นใจว่า log แก้ไขไม่ได้) ส่วน "แถว n" คือเลขแถวใน Features List

## Acceptance Criteria ต่อ User Story

### AC-1: บันทึก log เหตุการณ์ด้านการยืนยันตัวตน (แถว 1)
**อ้างอิง User Story:** US1 — "ในฐานะผู้ดูแลระบบ ฉันต้องการดู log กิจกรรมของผู้ใช้และระบบย้อนหลัง เพื่อสืบสวนเหตุการณ์ผิดปกติ"

- **Given** ผู้ใช้มีบัญชีในระบบ
- **When** ผู้ใช้เข้าสู่ระบบสำเร็จ หรือออกจากระบบ
- **Then** ระบบบันทึก log ของเหตุการณ์ login/logout นั้น พร้อมผลลัพธ์ "สำเร็จ"
- **Given** ผู้ใช้กรอกรหัสผ่านผิด
- **When** พยายามเข้าสู่ระบบ
- **Then** ระบบปฏิเสธการเข้าสู่ระบบ และบันทึก log ความพยายามที่ล้มเหลวพร้อมผลลัพธ์ "ล้มเหลว"
- **Given** ผู้ใช้ที่ไม่มีบัญชีอยู่จริง (username ไม่มีในระบบ)
- **When** พยายามเข้าสู่ระบบ
- **Then** ระบบบันทึก log ความพยายามล้มเหลวด้วย (ไม่ข้ามการบันทึก)

### AC-2: บันทึก log การสร้าง/แก้ไข/ลบเกรดหรือผลการเรียน (แถว 2)
**อ้างอิง User Story:** US1 — "เกรดถูกแก้ไขโดยใคร เมื่อใด"

- **Given** ผู้ใช้ที่มีสิทธิ์จัดการเกรด
- **When** สร้าง แก้ไข หรือลบเกรด/ผลการเรียนของนักศึกษา
- **Then** ระบบบันทึก log ระบุผู้กระทำ เวลา และค่าก่อน-หลังการเปลี่ยนแปลง (กรณีสร้าง ค่าก่อน = ว่าง กรณีลบ ค่าหลัง = ว่าง)
- **Given** การแก้ไขเกรดล้มเหลว (เช่น ไม่ผ่านการตรวจสอบข้อมูล)
- **When** ระบบปฏิเสธการแก้ไข
- **Then** ระบบบันทึก log พร้อมผลลัพธ์ "ล้มเหลว" และเกรดเดิมไม่เปลี่ยน

### AC-3: บันทึก log การเข้าถึงข้อมูลนักศึกษาคนอื่น (แถว 3)
**อ้างอิง User Story:** US1 — สืบสวนเหตุการณ์ผิดปกติ

- **Given** แอดมินหรืออาจารย์ล็อกอินอยู่
- **When** เปิดดูข้อมูลส่วนบุคคลของนักศึกษาคนอื่น (เช่น ประวัติผลการเรียน)
- **Then** ระบบบันทึก log ระบุผู้เปิดดู นักศึกษาเจ้าของข้อมูล และเวลา
- **Given** นักศึกษาเปิดดูข้อมูลของตนเอง
- **When** เปิดหน้าประวัติผลการเรียนของตน
- **Then** ไม่ถือเป็น "การเข้าถึงข้อมูลนักศึกษาคนอื่น" (ไม่ต้องสร้าง log ประเภทนี้) _(สมมติฐาน: spec ระบุเฉพาะการเข้าถึงโดยแอดมิน/อาจารย์)_

### AC-4: บันทึก log การเปลี่ยนสิทธิ์/บทบาท (แถว 4)
**อ้างอิง User Story:** US1 — สืบสวนเหตุการณ์ผิดปกติ

- **Given** แอดมินอยู่ที่คิวอนุมัติผู้แนะนำในห้องแชท
- **When** approve (หรือ reject) นักศึกษาเป็นผู้แนะนำ หรือเปลี่ยน role/permission ผู้ใช้
- **Then** ระบบบันทึก log การเปลี่ยนสิทธิ์ ระบุผู้ดำเนินการ ผู้ถูกเปลี่ยน บทบาทก่อน-หลัง และเวลา

### AC-5: บันทึก log การ export/ดาวน์โหลดข้อมูลชุดใหญ่ (แถว 5)
**อ้างอิง User Story:** US1 — สืบสวนเหตุการณ์ผิดปกติ

- **Given** ผู้ใช้ที่มีสิทธิ์ export ข้อมูล
- **When** export หรือดาวน์โหลดข้อมูลชุดใหญ่ออกจากระบบ
- **Then** ระบบบันทึก log ระบุผู้กระทำ ชุดข้อมูลที่ export และเวลา
- **Given** ผู้ใช้ไม่มีสิทธิ์ export
- **When** พยายาม export
- **Then** ระบบปฏิเสธ และบันทึก log พร้อมผลลัพธ์ "ล้มเหลว"
- _(ต้องการข้อมูลเพิ่มเติมจากผู้ใช้: นิยามเกณฑ์ "ข้อมูลชุดใหญ่")_

### AC-6: บันทึก log คำร้องใช้สิทธิตาม PDPA และผลการดำเนินการ (แถว 6)
**อ้างอิง User Story:** US3, US4 — ร้องขอใช้สิทธิ และสถาบันมีกระบวนการรองรับคำร้อง

- **Given** เจ้าของข้อมูลยื่นคำร้องใช้สิทธิ
- **When** คำร้องถูกสร้างในระบบ
- **Then** ระบบบันทึก log การรับคำร้อง
- **Given** คำร้องกำลังถูกดำเนินการ
- **When** เจ้าหน้าที่ PDPA ดำเนินการเสร็จ (สำเร็จ/ปฏิเสธบางส่วน/ล้มเหลว)
- **Then** ระบบบันทึก log ผลการดำเนินการ ผู้ดำเนินการ และเวลา

### AC-7: โครงสร้างรายการ log มาตรฐาน (แถว 7)
**อ้างอิง User Story:** US1 — ดู log ย้อนหลังเพื่อสืบสวน

- **Given** มีเหตุการณ์ที่ต้องบันทึกประเภทใดก็ได้ตาม AC-1 ถึง AC-6
- **When** ระบบสร้างรายการ log
- **Then** ทุกรายการมีครบ: ผู้กระทำ (actor), การกระทำ (action), เวลา (timestamp), เป้าหมาย/ทรัพยากร, ผลลัพธ์ (สำเร็จ/ล้มเหลว)
- **Given** เหตุการณ์ที่ระบบเป็นผู้กระทำเอง (เช่น งานลบข้อมูลอัตโนมัติ)
- **When** ระบบบันทึก log
- **Then** actor ระบุเป็นระบบ (system) ไม่เป็นค่าว่าง

### AC-8: Log แบบ immutable / tamper-evident (แถว 8)
**อ้างอิง User Story:** US5 — "ฉันต้องการมั่นใจว่า log ที่บันทึกไว้ไม่สามารถถูกแก้ไขหรือลบโดยผู้ใช้ทั่วไปได้"

- **Given** มี log ย้อนหลังอยู่ในระบบ
- **When** ผู้ใช้ทั่วไปหรือแอดมินระดับปกติพยายามแก้ไขหรือลบ log
- **Then** ระบบปฏิเสธ log เดิมไม่เปลี่ยน และความพยายามนั้นถูกบันทึกเป็น log
- **Given** log ถูกแก้ไขนอกช่องทางปกติ (จำลองการดัดแปลง)
- **When** ผู้ตรวจสอบตรวจความสมบูรณ์ของ log
- **Then** ระบบแสดงว่าตรวจพบความผิดปกติ (tamper-evident) _(สมมติฐาน: มีตัวบ่งชี้ความสมบูรณ์ตาม journey ผู้ตรวจสอบ)_

### AC-9: จำกัดสิทธิ์เข้าถึง log และ log-of-logs (แถว 9)
**อ้างอิง User Story:** US1, US5 — เฉพาะบทบาทที่ได้รับอนุญาตดู log

- **Given** ผู้ใช้เป็นผู้ตรวจสอบ/แอดมินระดับสูงที่ได้รับอนุญาต
- **When** เปิดหน้า log
- **Then** เข้าถึงได้ และระบบบันทึก log การเข้าถึงนั้น (log-of-logs)
- **Given** ผู้ใช้เป็นนักศึกษา อาจารย์ หรือแอดมินทั่วไป _(สมมติฐาน: ไม่ใช่ผู้ตรวจสอบ)_
- **When** พยายามเข้าหน้า log
- **Then** ระบบปฏิเสธการเข้าถึง และบันทึกความพยายามนั้น
- **Given** ผู้ตรวจสอบเปิดดู log ที่มีข้อมูลส่วนบุคคล
- **When** ดูรายละเอียดรายการ
- **Then** การเข้าถึงนั้นถูกบันทึกด้วย

### AC-10: หน้าค้นหา/ดู log ย้อนหลัง (แถว 10)
**อ้างอิง User Story:** US1 — "ดู log กิจกรรมของผู้ใช้และระบบย้อนหลัง"

- **Given** ผู้ตรวจสอบอยู่ที่หน้า log และมี log หลายประเภท
- **When** ค้นหา/กรองตามผู้กระทำ ช่วงเวลา หรือประเภทเหตุการณ์
- **Then** แสดงเฉพาะรายการที่ตรงเงื่อนไข เรียงตามเวลา และเปิดดูรายละเอียด (ค่าก่อน-หลัง ผลลัพธ์) ได้
- **Given** เงื่อนไขค้นหาที่ไม่มี log ตรงกัน
- **When** ค้นหา
- **Then** แสดงสถานะว่างอย่างเหมาะสม ไม่เกิดข้อผิดพลาด
- **Given** ต้องสืบสวนเหตุการณ์ที่เก่ากว่าระยะเก็บ log
- **When** ค้นหาช่วงเวลานั้น
- **Then** ไม่พบ log เพราะถูกลบตามระยะเก็บแล้ว

### AC-11: ระยะเวลาเก็บ log 1 ปี แบบ configurable (แถว 11)
**อ้างอิง User Story:** US1 — ตรวจสอบย้อนหลังตลอดรอบปีการศึกษา

- **Given** ค่าระยะเก็บ log = 1 ปี (ค่าเริ่มต้น)
- **When** ระบบรันการล้าง log ตามระยะเก็บ
- **Then** log ที่มีอายุไม่เกิน 1 ปียังคงอยู่ และ log ที่เกิน 1 ปีนับจากวันที่บันทึกถูกลบ
- **Given** ผู้มีสิทธิ์ปรับค่าระยะเก็บเป็นค่าอื่น
- **When** ระบบรันการล้างรอบถัดไป
- **Then** ใช้ค่าใหม่ในการตัดสิน และการเปลี่ยนค่านี้ถูกบันทึก log

### AC-12: ระบุฐานทางกฎหมายและแจ้ง privacy notice (แถว 12, 13)
**อ้างอิง User Story:** US2 — "ต้องการทราบว่าข้อมูลของฉันถูกเก็บไปเพื่อวัตถุประสงค์ใด"

- **Given** ผู้ใช้เข้าใช้ฟีเจอร์ที่เก็บข้อมูลส่วนบุคคล
- **When** ระบบเริ่มเก็บข้อมูลนั้น (ก่อนหรือขณะเก็บ)
- **Then** แสดง privacy notice ระบุวัตถุประสงค์และฐานทางกฎหมายของข้อมูลประเภทนั้น
- **Given** ข้อมูลจำเป็นต่อภารกิจการศึกษา (เช่น ผลการเรียน)
- **When** ระบบประมวลผลข้อมูล
- **Then** ใช้ฐาน "ภารกิจทางการศึกษา/สัญญา" และไม่บังคับให้ขอ consent
- **Given** ข้อมูลที่ไม่จำเป็นโดยตรง (เช่น การเข้าห้องแชท)
- **When** ผู้ใช้จะเริ่มใช้ฟีเจอร์
- **Then** ใช้ฐาน "consent" และระบบแจ้งวัตถุประสงค์ก่อน

### AC-13: ขอและจัดการ consent (แถว 14)
**อ้างอิง User Story:** US2 — "ให้/ถอนความยินยอมได้ตามความสมัครใจ"

- **Given** ผู้ใช้ยังไม่ให้ consent สำหรับฟีเจอร์ที่ใช้ฐาน consent
- **When** ผู้ใช้ไม่กดยินยอม
- **Then** ผู้ใช้ใช้ฟีเจอร์นั้นไม่ได้ และข้อมูลที่ต้องอาศัย consent ไม่ถูกเก็บ
- **Given** ผู้ใช้ติ๊ก/กดยินยอมอย่างชัดแจ้ง
- **When** ยืนยัน
- **Then** ระบบบันทึก consent (เวลา วัตถุประสงค์) และอนุญาตใช้ฟีเจอร์ (consent ต้องไม่ถูกติ๊กไว้ล่วงหน้า)
- **Given** ผู้ใช้เคยให้ consent
- **When** ถอนความยินยอมที่หน้าจัดการ consent
- **Then** ระบบหยุดประมวลผลข้อมูลตาม consent นั้น (เช่น ออกจากห้องแชท/หยุดใช้ฟีเจอร์) และบันทึกการถอน _(สมมติฐาน: ผลของการถอนตาม journey)_
- **Given** ผู้ใช้ถอน consent
- **When** ตรวจข้อความที่เคยโพสต์ในห้องแชท
- **Then** _(ต้องการข้อมูลเพิ่มเติมจากผู้ใช้: spec ยังไม่ระบุการจัดการข้อความเดิม)_

### AC-14: ยื่นคำร้องใช้สิทธิของเจ้าของข้อมูล (แถว 15)
**อ้างอิง User Story:** US3 — "ร้องขอเข้าถึง แก้ไข หรือลบข้อมูลส่วนบุคคลของฉัน"

- **Given** เจ้าของข้อมูลล็อกอินอยู่ _(สมมติฐาน: ยื่นผ่านฟอร์มในระบบ)_
- **When** ยื่นคำร้องประเภทเข้าถึง/แก้ไข/ลบ/คัดค้าน/โอนย้ายข้อมูล พร้อมข้อมูลครบ
- **Then** ระบบรับคำร้อง สร้างรายการในคิว และแจ้งยืนยันการรับคำร้อง
- **Given** กรอกข้อมูลคำร้องไม่ครบ (เช่น ไม่เลือกประเภทสิทธิ)
- **When** กดส่ง
- **Then** ระบบไม่ส่งคำร้อง และแสดงข้อความระบุข้อมูลที่ขาด
- **Given** เจ้าของข้อมูลขอลบข้อมูลที่ต้องเก็บตามระเบียบ (เช่น ทรานสคริปต์)
- **When** คำร้องถูกดำเนินการ
- **Then** ปฏิเสธเฉพาะส่วนนั้นพร้อมแจ้งเหตุผล ส่วนที่ลบได้ดำเนินการตามปกติ

### AC-15: กระบวนการภายในของสถาบันรองรับคำร้อง (แถว 16)
**อ้างอิง User Story:** US4 — "ต้องการมีกระบวนการรองรับคำร้องขอใช้สิทธิของเจ้าของข้อมูล"

- **Given** มีคำร้องในคิวของเจ้าหน้าที่ PDPA
- **When** เจ้าหน้าที่ตรวจสอบตัวตนผู้ร้องและขอบเขตคำร้อง แล้วดำเนินการ (เข้าถึง/แก้ไข/ลบ/โอนย้าย)
- **Then** ระบบดำเนินการตามสิทธิที่ร้องขอ ตอบกลับเจ้าของข้อมูล และเปลี่ยนสถานะคำร้อง
- **Given** ผู้ร้องไม่ผ่านการยืนยันตัวตน _(สมมติฐาน: ตรวจจากบัญชีที่ล็อกอิน)_
- **When** เจ้าหน้าที่ตรวจสอบ
- **Then** คำร้องไม่ถูกดำเนินการ และมีการแจ้งเหตุผลกลับ
- **Given** ผู้ใช้ที่ไม่ใช่เจ้าหน้าที่ PDPA
- **When** พยายามเปิดคิวคำร้อง
- **Then** ระบบปฏิเสธการเข้าถึง
- **Given** มีคำร้องจำนวนมากเข้ามาพร้อมกัน
- **When** ระบบรับคำร้อง
- **Then** ทุกคำร้องถูกรับเข้าคิวครบ ไม่สูญหาย (ไม่ทดสอบ SLA เพราะ spec ไม่ระบุ)

### AC-16: ลบ/ทำลาย/anonymize ข้อมูลเมื่อพ้นระยะเก็บ (แถว 17)
**อ้างอิง User Story:** US2, US4 — จัดการข้อมูลตามระยะเวลาและสิทธิของเจ้าของข้อมูล

- **Given** นักศึกษายังมีสถานภาพ หรือพ้นสถานภาพไม่เกิน 5 ปี
- **When** ระบบรันกระบวนการลบข้อมูลตามระยะเก็บ
- **Then** ข้อมูลส่วนบุคคลยังคงอยู่
- **Given** นักศึกษาพ้นสถานภาพเกิน 5 ปี
- **When** ระบบรันกระบวนการลบข้อมูล
- **Then** ข้อมูลถูกลบหรือ anonymize จนระบุตัวตนไม่ได้ และการดำเนินการถูกบันทึก log
- **Given** ข้อมูลที่ระเบียบกำหนดให้เก็บถาวร (เช่น ทรานสคริปต์)
- **When** พ้นระยะ 5 ปี
- **Then** ข้อมูลส่วนนั้นไม่ถูกลบ

### AC-17: มาตรการความปลอดภัยของข้อมูล (แถว 18)
**อ้างอิง User Story:** US4, US5 — มาตรการคุ้มครองข้อมูลและ log

- **Given** ข้อมูลส่วนบุคคลและ log ที่จัดเก็บในระบบ
- **When** ตรวจสอบการจัดเก็บและการส่งผ่าน
- **Then** ข้อมูลถูกเข้ารหัสทั้งขณะจัดเก็บและส่งผ่าน
- **Given** บัญชีผู้ดูแลระบบ/ผู้ตรวจสอบ
- **When** เข้าสู่ระบบ
- **Then** ต้องยืนยันตัวตนหลายขั้น (MFA) จึงเข้าได้
- **Given** ผู้ใช้แต่ละบทบาท
- **When** เข้าถึงข้อมูลส่วนบุคคล
- **Then** เข้าถึงได้เท่าที่จำเป็นตามหลัก least privilege เท่านั้น

### AC-18: กระบวนการแจ้งเหตุข้อมูลรั่วไหลภายใน 72 ชั่วโมง (แถว 19)
**อ้างอิง User Story:** US4 — "มีมาตรการแจ้งเหตุเมื่อข้อมูลรั่วไหล"

- **Given** ตรวจพบเหตุข้อมูลรั่วไหล ณ เวลา T
- **When** เจ้าหน้าที่ประเมินความรุนแรงตามกระบวนการ
- **Then** มีบันทึกการประเมิน และหากเข้าเกณฑ์ต้องแจ้ง สคส./เจ้าของข้อมูลภายใน 72 ชั่วโมงนับจาก T
- **Given** ทีม Processor พบเหตุก่อนสถาบัน
- **When** พบเหตุ
- **Then** ส่งต่อให้ Controller ทันที โดยการนับ 72 ชม. เริ่มจากเวลาที่ทราบเหตุ _(สมมติฐานตาม journey)_
- **Given** เหตุที่ประเมินแล้วไม่เข้าเกณฑ์ต้องแจ้ง
- **When** สรุปผลประเมิน
- **Then** มีการบันทึกเหตุผลของการไม่แจ้ง _(ต้องการข้อมูลเพิ่มเติมจากผู้ใช้: spec ไม่ระบุเกณฑ์ตัดสิน)_

### AC-19: กำหนดบทบาท Data Controller / Data Processor (แถว 20)
**อ้างอิง User Story:** US4 — สถาบันในฐาน Data Controller

- **Given** เอกสาร/การตั้งค่าบทบาทของระบบ
- **When** ตรวจสอบการกำหนดบทบาท
- **Then** สถาบัน = Data Controller (กำหนดวัตถุประสงค์) และทีมพัฒนา = Data Processor (ประมวลผลตามขอบเขตที่สถาบันกำหนด)
- **Given** Processor ต้องการประมวลผลข้อมูลนอกขอบเขตที่ Controller กำหนด
- **When** ดำเนินการ
- **Then** ไม่อนุญาต และมีการบันทึก log

### AC-20: ใช้หลักการ PDPA กับเนื้อหาแชทที่อ้างถึงข้อมูลส่วนบุคคลของผู้อื่น (แถว 21)
**อ้างอิง User Story:** US2, US4 — เนื้อหาแชทอยู่ภายใต้หลักการเดียวกัน

- **Given** ข้อความในห้องแชทอ้างถึงข้อมูลส่วนบุคคลของนักศึกษาอื่น
- **When** เจ้าของข้อมูลที่ถูกอ้างถึงยื่นคำร้องเข้าถึง/ลบข้อมูลนั้น
- **Then** ข้อความดังกล่าวอยู่ในขอบเขตการดำเนินการตามคำร้อง เช่นเดียวกับข้อมูลส่วนบุคคลประเภทอื่น
- **Given** เจ้าหน้าที่/ผู้ตรวจสอบเข้าถึงเนื้อหาแชท
- **When** เปิดดูข้อความ
- **Then** การเข้าถึงนั้นถูกบันทึก log

### AC-21: ติดตามสถานะคำร้องสำหรับเจ้าของข้อมูล (แถว 22, Could have)
**อ้างอิง User Story:** US3 — ร้องขอเข้าถึง/แก้ไข/ลบ (ผลการดำเนินการ)

- **Given** เจ้าของข้อมูลเคยยื่นคำร้อง
- **When** เปิดหน้าสถานะคำร้องของตน _(สมมติฐาน: spec ไม่ได้ระบุตรงๆ)_
- **Then** เห็นสถานะปัจจุบันของคำร้องตนเอง และไม่เห็นคำร้องของผู้อื่น

## ฟีเจอร์ที่ไม่มี AC (Won't have this time ตาม Out of Scope)
แถว 23 (ระบบแจ้งเตือน breach อัตโนมัติ), แถว 24 (เลือกเครื่องมือ/สถาปัตยกรรม logging), แถว 25 (ร่าง privacy policy/สัญญาประมวลผลข้อมูลฉบับสมบูรณ์), แถว 26 (GDPR/กฎหมายต่างประเทศ) — ไม่ระบุ AC เพื่อ traceability เท่านั้น
