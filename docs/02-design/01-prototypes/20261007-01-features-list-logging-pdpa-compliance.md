# Features List: การเก็บ Log กิจกรรมและการปฏิบัติตาม PDPA

**สร้างจาก:** [[../../01-requirements/01-spec/20260825-03-logging-pdpa-compliance|การเก็บ Log กิจกรรมและการปฏิบัติตาม PDPA]]
**วันที่สร้าง:** 2026-10-07

## รายการฟีเจอร์ (MoSCoW)

| # | ฟีเจอร์ | คำอธิบาย | อ้างอิง User Story | MoSCoW |
|---|---|---|---|---|
| 1 | บันทึก log เหตุการณ์ด้านการยืนยันตัวตน | บันทึก login/logout และความพยายามเข้าสู่ระบบที่ล้มเหลว | US1 | Must have |
| 2 | บันทึก log การเปลี่ยนแปลงเกรด/ผลการเรียน | บันทึกการสร้าง/แก้ไข/ลบเกรด พร้อมผู้กระทำ เวลา และค่าก่อน-หลัง | US1 | Must have |
| 3 | บันทึก log การเข้าถึงข้อมูลนักศึกษาคนอื่น | บันทึกเมื่อแอดมิน/อาจารย์เปิดดูข้อมูลส่วนบุคคลของนักศึกษา (เช่น ประวัติผลการเรียน) | US1 | Must have |
| 4 | บันทึก log การเปลี่ยนสิทธิ์/บทบาท | บันทึกการเปลี่ยน role/permission เช่น การ approve ผู้แนะนำในห้องแชท | US1 | Must have |
| 5 | บันทึก log การ export/ดาวน์โหลดข้อมูลชุดใหญ่ | บันทึกการนำข้อมูลออกจากระบบเป็นชุดใหญ่ | US1 | Must have |
| 6 | บันทึก log คำร้องใช้สิทธิตาม PDPA | บันทึกคำร้องของเจ้าของข้อมูลและผลการดำเนินการ | US3, US4 | Must have |
| 7 | โครงสร้างรายการ log มาตรฐาน | ทุกรายการมี actor, action, timestamp, เป้าหมาย/ทรัพยากร, ผลลัพธ์ (สำเร็จ/ล้มเหลว) | US1 | Must have |
| 8 | Log แบบ immutable / tamper-evident | ผู้ใช้ทั่วไปและแอดมินระดับปกติแก้ไข/ลบ log ย้อนหลังไม่ได้ | US5 | Must have |
| 9 | จำกัดสิทธิ์เข้าถึง log + log-of-logs | เฉพาะบทบาทที่ได้รับอนุญาตดู log ได้ และการเข้าถึง log ถูกบันทึกเป็น log | US1, US5 | Must have |
| 10 | หน้าค้นหา/ดู log ย้อนหลัง | ผู้ตรวจสอบค้นหาและดู log ตามผู้กระทำ ช่วงเวลา ประเภทเหตุการณ์ เพื่อสืบสวนข้อพิพาท | US1 | Must have |
| 11 | ระยะเวลาเก็บ log 1 ปี แบบ configurable | เก็บ log 1 ปีนับจากวันที่บันทึก และปรับค่าได้ตามนโยบาย | US1 | Must have |
| 12 | ระบุฐานทางกฎหมายของข้อมูลแต่ละประเภท | กำหนดฐานต่อประเภทข้อมูล: ภารกิจการศึกษา (เช่น ผลการเรียน) หรือ consent (เช่น ห้องแชท) | US2, US4 | Must have |
| 13 | Privacy notice | แจ้งวัตถุประสงค์การเก็บข้อมูลก่อนหรือขณะเก็บ | US2 | Must have |
| 14 | การขอและจัดการ consent | ขอความยินยอมอย่างชัดแจ้งเมื่อไม่มีฐานอื่น ให้และถอนความยินยอมได้ | US2 | Must have |
| 15 | ยื่นคำร้องใช้สิทธิของเจ้าของข้อมูล | รองรับสิทธิเข้าถึง แก้ไข ลบ คัดค้าน และโอนย้ายข้อมูล (data portability) | US3 | Must have |
| 16 | กระบวนการภายในรองรับคำร้องของสถาบัน | สถาบัน (Data Controller) รับ ตรวจสอบ ดำเนินการ และตอบกลับคำร้องของเจ้าของข้อมูล | US4 | Must have |
| 17 | การลบ/ทำลาย/anonymize ข้อมูลเมื่อพ้นระยะเก็บ | ข้อมูลนักศึกษาเก็บตลอดสถานภาพ + 5 ปีหลังพ้นสถานภาพ แล้วลบหรือ anonymize เว้นแต่มีข้อกำหนดให้เก็บถาวร (เช่น ทรานสคริปต์) | US2, US4 | Must have |
| 18 | มาตรการความปลอดภัยของข้อมูล | เข้ารหัสขณะจัดเก็บ/ส่งผ่าน, least privilege, MFA สำหรับบัญชีแอดมิน | US4, US5 | Must have |
| 19 | กระบวนการแจ้งเหตุข้อมูลรั่วไหลภายใน 72 ชม. | ตรวจจับ ประเมินความรุนแรง และแจ้ง สคส./เจ้าของข้อมูล ภายใน 72 ชม. (ระดับนโยบาย) | US4 | Must have |
| 20 | กำหนดบทบาท Data Controller / Data Processor | สถาบัน = Controller, ทีมพัฒนา = Processor ประมวลผลตามขอบเขตที่สถาบันกำหนด | US4 | Should have |
| 21 | ใช้หลักการ PDPA กับเนื้อหาแชทที่อ้างถึงข้อมูลส่วนบุคคลของผู้อื่น | ข้อความในห้องแชทที่มีข้อมูลส่วนบุคคลของผู้อื่นอยู่ภายใต้หลักการเดียวกัน | US2, US4 | Should have |
| 22 | แดชบอร์ดสถานะคำร้อง/ติดตามผลสำหรับเจ้าของข้อมูล | ให้เจ้าของข้อมูลดูสถานะคำร้องของตนเอง _(สมมติฐาน: spec ไม่ได้ระบุตรงๆ)_ | US3 | Could have |
| 23 | ระบบแจ้งเตือนอัตโนมัติเมื่อเกิด breach | แจ้งเตือนอัตโนมัติในรายละเอียดทางเทคนิค | - | Won't have (this time) |
| 24 | เลือกเครื่องมือ/สถาปัตยกรรม logging | ไปกำหนดในขั้น 02-technical | - | Won't have (this time) |
| 25 | ร่าง privacy policy/สัญญาประมวลผลข้อมูลฉบับสมบูรณ์ | ต้องผ่านฝ่ายกฎหมาย/ผู้เชี่ยวชาญ PDPA | - | Won't have (this time) |
| 26 | การปฏิบัติตาม GDPR/กฎหมายต่างประเทศ | อยู่นอกขอบเขตเว้นแต่ระบุเพิ่มในอนาคต | - | Won't have (this time) |

หมายเหตุ: US1 = ผู้ดูแลระบบดู log ย้อนหลัง, US2 = เจ้าของข้อมูลรับรู้วัตถุประสงค์และให้/ถอน consent, US3 = เจ้าของข้อมูลร้องขอเข้าถึง/แก้ไข/ลบ, US4 = สถาบันรองรับคำร้องและแจ้งเหตุรั่วไหล, US5 = ผู้ดูแลระบบมั่นใจว่า log แก้ไขไม่ได้ (เรียงตามลำดับใน spec)

- **Must have** — ต้องมีเพื่อให้ requirement นี้ใช้งานได้ตามขอบเขต (In Scope) ที่ระบุใน spec
- **Should have** — สำคัญแต่เลื่อนออกไปทำทีหลังได้โดยไม่กระทบ business rule หลัก
- **Could have** — เสริม เอาออกได้โดยไม่กระทบการใช้งานหลัก
- **Won't have (this time)** — สอดคล้องกับ Out of Scope ของ spec (ระบุไว้เพื่อ traceability ไม่ใช่ฟีเจอร์ใหม่)
