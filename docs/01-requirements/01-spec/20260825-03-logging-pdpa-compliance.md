# การเก็บ Log กิจกรรมและการปฏิบัติตาม PDPA

**วันที่สร้าง:** 2026-08-25
**สถานะ:** New

## ภาพรวม (Overview)

ระบบ Grade Runway ต้องมีกลไกกลาง (cross-cutting) สองส่วนที่ทำงานคู่กันตลอดทั้งระบบ ไม่ผูกกับฟีเจอร์ใดฟีเจอร์หนึ่งโดยเฉพาะ ได้แก่:

1. **การเก็บ Log กิจกรรม (Audit Logging)** — บันทึกกิจกรรมสำคัญของผู้ใช้และระบบอย่างเป็นระบบ เพื่อใช้ตรวจสอบย้อนหลัง (traceability), สืบสวนเหตุการณ์ผิดปกติ, และเป็นหลักฐานประกอบการปฏิบัติตามกฎหมาย
2. **การปฏิบัติตาม PDPA (พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562)** — กำหนดแนวทางการเก็บ ใช้ เปิดเผย และคุ้มครองข้อมูลส่วนบุคคลของนักศึกษาและผู้ใช้งานทุกกลุ่มในระบบ ให้สอดคล้องกับสิทธิของเจ้าของข้อมูลตามกฎหมาย

เนื่องจากระบบ Grade Runway จัดเก็บข้อมูลที่มีความอ่อนไหว เช่น ผลการเรียน พฤติกรรมการเรียน และเนื้อหาการสนทนาในห้องแชท (ตามที่ระบุใน [[20260825-01-personalized-learning-reminder|ระบบเตือนและแนะนำแนวทางการเรียนส่วนบุคคล]] และ [[20260825-02-high-grade-peer-review-chat|ช่องแชทรีวิวและแนะนำวิธีการเรียนจากนักศึกษาเกรดสูง]]) ทั้งสองเรื่องนี้จึงเป็นข้อกำหนดพื้นฐาน (baseline requirement) ที่ทุกฟีเจอร์ในระบบต้องปฏิบัติตาม

## User Stories / Use Cases

- ในฐานะผู้ดูแลระบบ ฉันต้องการดู log กิจกรรมของผู้ใช้และระบบย้อนหลัง เพื่อสืบสวนเหตุการณ์ผิดปกติหรือข้อพิพาทที่เกิดขึ้น (เช่น เกรดถูกแก้ไขโดยใคร เมื่อใด)
- ในฐานะเจ้าของข้อมูลส่วนบุคคล (นักศึกษา/บุคลากร) ฉันต้องการทราบว่าข้อมูลของฉันถูกเก็บไปเพื่อวัตถุประสงค์ใด และสามารถให้/ถอนความยินยอมได้ตามความสมัครใจ
- ในฐานะเจ้าของข้อมูลส่วนบุคคล ฉันต้องการร้องขอเข้าถึง แก้ไข หรือลบข้อมูลส่วนบุคคลของฉันได้ตามสิทธิที่กฎหมายกำหนด
- ในฐานะสถาบันการศึกษา (Data Controller) ฉันต้องการมีกระบวนการรองรับคำร้องขอใช้สิทธิของเจ้าของข้อมูล และมีมาตรการแจ้งเหตุเมื่อข้อมูลรั่วไหล เพื่อให้สอดคล้องกับ พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล
- ในฐานะผู้ดูแลระบบ ฉันต้องการมั่นใจว่า log ที่บันทึกไว้ไม่สามารถถูกแก้ไขหรือลบโดยผู้ใช้ทั่วไปได้ เพื่อรักษาความน่าเชื่อถือของหลักฐาน

## Business Rules

### การเก็บ Log กิจกรรม (Audit Logging)

- ระบบต้องบันทึก log อย่างน้อยสำหรับเหตุการณ์ต่อไปนี้:
  - การเข้าสู่ระบบ/ออกจากระบบ (login/logout) และความพยายามเข้าสู่ระบบที่ล้มเหลว
  - การสร้าง/แก้ไข/ลบเกรดหรือผลการเรียน (ระบุผู้กระทำ, เวลา, ค่าก่อน-หลังการเปลี่ยนแปลง)
  - การเข้าถึงข้อมูลส่วนบุคคลของนักศึกษาคนอื่นโดยผู้ดูแลระบบ/อาจารย์ (เช่น การเปิดดูประวัติผลการเรียน)
  - การเปลี่ยนแปลงสิทธิ์/บทบาทผู้ใช้ (role/permission change) เช่น การ approve ผู้แนะนำในห้องแชท
  - การส่งออก (export) หรือดาวน์โหลดข้อมูลชุดใหญ่ออกจากระบบ
  - การร้องขอใช้สิทธิของเจ้าของข้อมูลตาม PDPA และผลการดำเนินการ
- แต่ละรายการ log ต้องบันทึกอย่างน้อย: ผู้กระทำ (actor), การกระทำ (action), เวลา (timestamp), เป้าหมาย/ทรัพยากรที่ถูกกระทำ, และผลลัพธ์ (สำเร็จ/ล้มเหลว)
- log ต้องมีคุณสมบัติ **immutable / tamper-evident** — ผู้ใช้ทั่วไปและผู้ดูแลระบบระดับปกติต้องไม่สามารถแก้ไขหรือลบ log ย้อนหลังได้
- การเข้าถึง log ต้องจำกัดเฉพาะบทบาทที่ได้รับอนุญาต (เช่น ผู้ดูแลระบบระดับสูง/ผู้ตรวจสอบ) และการเข้าถึง log เองก็ต้องถูกบันทึกเป็น log ด้วย (log-of-logs)
- **ระยะเวลาการเก็บ log กิจกรรม: 1 ปี** นับจากวันที่บันทึก (สมดุลระหว่างต้นทุนพื้นที่จัดเก็บกับความสามารถในการตรวจสอบย้อนหลังตลอดรอบปีการศึกษา) โดยควรออกแบบให้เป็นค่า configurable เผื่อต้องปรับตามนโยบายในอนาคต

### การปฏิบัติตาม PDPA

- ระบบต้องระบุ**ฐานทางกฎหมาย (legal basis)** ของการประมวลผลข้อมูลส่วนบุคคลแต่ละประเภทอย่างชัดเจน โดยยึดหลักว่าข้อมูลที่จำเป็นต่อภารกิจการจัดการศึกษา (เช่น ผลการเรียน, ทะเบียนนักศึกษา) ใช้ฐาน "การปฏิบัติตามสัญญา/ภารกิจทางการศึกษา" ส่วนข้อมูลที่ไม่จำเป็นโดยตรง (เช่น การเข้าร่วมห้องแชทแนะนำวิธีเรียน) ใช้ฐาน "ความยินยอม (consent)"
- ระบบต้อง**แจ้งวัตถุประสงค์การเก็บข้อมูล (privacy notice)** ให้ผู้ใช้ทราบก่อนหรือขณะเก็บข้อมูล และต้องขอ**ความยินยอม (consent)** อย่างชัดแจ้งในกรณีที่การประมวลผลไม่ได้อาศัยฐานทางกฎหมายอื่น
- ระบบต้องรองรับ**สิทธิของเจ้าของข้อมูล** ตามที่กฎหมายกำหนด ได้แก่ สิทธิเข้าถึงข้อมูล, สิทธิขอแก้ไขข้อมูลให้ถูกต้อง, สิทธิขอลบข้อมูล, สิทธิถอนความยินยอม, สิทธิคัดค้านการประมวลผล, และสิทธิขอโอนย้ายข้อมูล (data portability)
- **ระยะเวลาการเก็บข้อมูลส่วนบุคคลของนักศึกษา:** ตลอดระยะเวลาที่มีสถานภาพนักศึกษา บวกเพิ่มอีก **5 ปีหลังจบการศึกษา/พ้นสถานภาพ** เพื่อรองรับการขอเอกสารย้อนหลังหรือข้อพิพาททางวิชาการ เมื่อพ้นระยะเวลาดังกล่าวต้องมีกระบวนการลบ/ทำลายหรือทำให้ไม่สามารถระบุตัวตนได้ (anonymize) เว้นแต่มีข้อกำหนดอื่นทางกฎหมายหรือระเบียบของสถาบัน (เช่น ทรานสคริปต์ที่ต้องเก็บถาวรตามระเบียบทะเบียน) ที่ให้เก็บนานกว่านี้
- ระบบต้องมี**มาตรการรักษาความปลอดภัยของข้อมูล** ที่เหมาะสม เช่น การเข้ารหัสข้อมูล (encryption) ทั้งขณะจัดเก็บและส่งผ่าน, การควบคุมสิทธิ์การเข้าถึงตามหลัก least privilege, การยืนยันตัวตนหลายขั้น (MFA) สำหรับบัญชีผู้ดูแลระบบ
- ระบบต้องมี**กระบวนการแจ้งเหตุข้อมูลรั่วไหล (data breach notification)** ต่อผู้ที่เกี่ยวข้อง (สำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล และ/หรือเจ้าของข้อมูล) **ภายใน 72 ชั่วโมง** นับจากที่ทราบเหตุ โดยต้องมีกระบวนการภายในสำหรับตรวจจับ ประเมินความรุนแรง และแจ้งเหตุตามกรอบเวลานี้
- **Data Controller (ผู้ควบคุมข้อมูลส่วนบุคคล):** สถาบันการศึกษา (มหาวิทยาลัย) เป็นผู้ควบคุมข้อมูลส่วนบุคคลตาม PDPA และเป็นผู้กำหนดวัตถุประสงค์การเก็บข้อมูล ส่วนทีมพัฒนา/ผู้ให้บริการระบบ Grade Runway ทำหน้าที่เป็น **Data Processor** ที่ประมวลผลข้อมูลตามคำสั่งและขอบเขตที่สถาบันกำหนด
- ข้อความ/เนื้อหาที่นักศึกษาโพสต์ในห้องแชท (ตามเอกสาร [[20260825-02-high-grade-peer-review-chat|ช่องแชทรีวิวและแนะนำวิธีการเรียนจากนักศึกษาเกรดสูง]]) ที่มีการอ้างอิงถึงข้อมูลส่วนบุคคลของผู้อื่น ต้องอยู่ภายใต้หลักการเดียวกันนี้ด้วย

## ขอบเขต (Scope)

### อยู่ในขอบเขต (In Scope)

- การออกแบบและบังคับใช้กลไก audit logging สำหรับเหตุการณ์สำคัญทั่วทั้งระบบ
- การกำหนดนโยบายและกลไกรองรับสิทธิของเจ้าของข้อมูลตาม PDPA (เข้าถึง/แก้ไข/ลบ/ถอนความยินยอม/โอนย้ายข้อมูล)
- การกำหนดระยะเวลาการเก็บรักษาและการทำลายข้อมูลส่วนบุคคลเมื่อพ้นความจำเป็น
- มาตรการรักษาความปลอดภัยพื้นฐานของข้อมูลส่วนบุคคลและ log
- กระบวนการแจ้งเหตุข้อมูลรั่วไหลในระดับนโยบาย (ยังไม่รวมการออกแบบระบบแจ้งเตือนอัตโนมัติในรายละเอียดทางเทคนิค)

### ไม่อยู่ในขอบเขต (Out of Scope)

- การออกแบบสถาปัตยกรรมทางเทคนิคของระบบ logging (เช่น เลือกใช้เครื่องมือ/แพลตฟอร์มใด) — จะถูกกำหนดต่อในขั้นตอน [[../../02-design/02-technical/index|02-technical]]
- การร่างเอกสารทางกฎหมาย (privacy policy ฉบับสมบูรณ์, สัญญาประมวลผลข้อมูล) ที่ต้องผ่านการตรวจสอบโดยฝ่ายกฎหมาย/ผู้เชี่ยวชาญด้าน PDPA โดยตรง
- การขอความยินยอมหรือการปฏิบัติตามกฎหมายคุ้มครองข้อมูลของประเทศอื่นนอกเหนือจากประเทศไทย (เช่น GDPR) — เว้นแต่จะมีการระบุเพิ่มเติมในอนาคต
